# tickets

티켓 하나의 일생을 처음부터 끝까지 다루는 스킬이다.
관찰된 문제가 Notion에 기록되고, 공개 GitHub Issue로 발행되고, 계약을 벗어나지 않은 PR이 되어 닫힌다.

세 단계를 한 스킬에 둔 이유는 단계마다 계약이 달라지기 때문이 아니라 **같기** 때문이다.
Notion 본문에 쓴 `최소 요구`·`완료 조건`·`절대 금지`가 Issue의 같은 세 섹션이 되고, 그 세 섹션이 PR의 범위가 된다.
세 곳이 갈리면 티켓은 실행 불가능해지므로, 한 계약이 세 표면을 통과하는 동안 형태만 바뀌고 내용은 바뀌지 않게 하는 것이 이 스킬의 일이다.

## 원본 위치

| 정보 | 원본(canonical) | 다른 곳에 남기는 것 |
| --- | --- | --- |
| QA 관찰·증거·제3자 캡처 | Notion `🐞 QA 요청` 행 | 없음 |
| 실행 계약과 진행 상태 | GitHub Issue·PR | Notion `GitHub Issue` 속성의 URL |
| 저장소 규칙·브랜치·커밋·보안 | [AGENTS.md](../../AGENTS.md)와 그 링크 문서 | 없음 — 이 스킬은 규칙을 복제하지 않는다 |

이 스킬은 AGENTS.md의 규칙을 옮겨 적지 않는다.
사본을 만들면 원본이 바뀔 때 조용히 갈라지고, 갈라진 사본을 따른 작업은 리뷰에서야 발견된다.

## 어느 단계인지 먼저 정한다

| 사용자가 하는 말 | 단계 | 절차 |
| --- | --- | --- |
| "QA 티켓 만들어줘", "이 문제 티켓으로", "티켓 다시 써줘" | 1. 작성 | [§1](#1-작성--notion에-티켓을-쓴다) |
| "GitHub에 이슈로 올려줘", "이 행 배포해줘", "이슈랑 연결해줘" | 2. 발행 | [§2](#2-발행--notion-행을-github-issue로-내보낸다) |
| "oss-hub 티켓 #123 진행해줘" | 3. 수행 | [§3](#3-수행--issue를-pr로-만든다) |
| "릴리스 QA 돌려줘", "결함 찾아줘" | — | 이 스킬이 아니라 `run-release-qa` |

한 요청이 두 단계를 걸치는 일은 흔하다 — "티켓 쓰고 이슈까지 올려줘"는 1단계 뒤 2단계다.
그때도 단계를 건너뛰지 않는다. Notion 행 없이 Issue를 만들면 증거가 어디에도 남지 않는다.

## 누가 할 수 있나

**티켓 작성·발행은 팀원 누구나 한다.**
`docs/handoff/team-state/`에 저널 파일이 있는 사람은 Notion 행을 만들고 GitHub Issue를 발행할 수 있다.
이전에는 두 사람만 발행할 수 있었지만, 문제를 관찰한 사람과 티켓을 쓸 수 있는 사람이 다르면 관찰은 대화 속에서 사라진다.

발행권을 넓히는 대신 아래 세 가지는 넓히지 않는다.

- 담당자는 0명 또는 1명이며, 남을 담당자로 지정하려면 그 사람의 동의가 있어야 한다. 스스로를 지정하는 것은 언제나 가능하다.
- 남이 만든 티켓의 본문 교체, 행 삭제, Issue 종료는 그 티켓의 작성자나 담당자만 한다. 다른 사람은 코멘트로 제안한다.
- `완료 여부`는 사람이 배포 환경에서 완료 조건을 전부 확인한 뒤에만 체크한다. 에이전트는 체크하지 않는다.

## 공통 가드레일

1. 어떤 쓰기 작업이든 하기 전에 [AGENTS.md](../../AGENTS.md)와 [보안 규칙](../../docs/rules/security.md)을 읽는다.
2. 티켓을 관리하는 동안 제품 코드, 배포 상태, 계정, 테스트 데이터를 바꾸지 않는다. 3단계의 구현은 예외이며 그때는 티켓 계약이 범위다.
3. 화면 티켓은 화면 하나와 논리 변경 하나를, 화면 없는 티켓은 산출물 위치 하나와 논리 변경 하나를 다룬다.
4. 실데이터, 개인정보, 자격증명, private 저장소 세부를 어느 표면에도 넣지 않는다.
5. 기록되지 않은 역할·재현 절차·기대 결과·의존성·구현 경계를 추론하지 않는다. 없으면 `미기록`, 확인하지 못했으면 `확인 필요`로 남긴다.
6. 사용자가 요청하지 않은 Notion 행이나 GitHub Issue를 만들거나 고치지 않는다. 초안을 보여 달라는 요청은 발행 허가가 아니다.

## 1. 작성 — Notion에 티켓을 쓴다

### 1.1 지금의 데이터베이스를 읽는다

초안을 쓰기 전에 현재 schema, 기본 템플릿, 보이는 행, 그리고 가장 큰 `QA<번호>`를 읽는다.
속성과 본문 계약의 원본은 [notion-ticket-contract.md](references/notion-ticket-contract.md)다.
살아 있는 schema가 번들된 계약과 다르면 대체 필드를 지어내지 말고 멈춰서 묻는다.

### 1.2 만들기 직전에 중복을 확인한다

행을 만들기 바로 전에 Notion을 다시 조회한다.
아래 중 하나라도 기존 행과 맞으면 새 행을 만들지 않고 그 행을 고치거나 참조한다.

- 핵심 제목 구절이 같거나 한쪽이 다른 쪽을 포함한다.
- 경로, 페르소나, 증상 요약이 같다.
- 핵심 문제 문장이 같은 실패·같은 경로·같은 역할을 서술한다.
- 증거가 같은 기준 SHA나 같은 QA 회차를 가리킨다.

원인 추정이 다르다는 것은 새 행을 만들 이유가 되지 않는다.
사용자에게 보이는 증상과 재현이 같으면 같은 티켓이다.

### 1.3 사실을 정규화한다

제목은 `QA<번호>. <관찰된 증상>` 형태로 증상을 앞세운다.
번호는 현재 최댓값 다음을 쓰고 삭제된 번호를 재사용하지 않는다.

작업 유형은 하나만 고른다.

- `fix`: 관찰된 동작이 기대 동작과 어긋난다.
- `feat`: 요청된 사용자 능력이 아직 없다.
- `refactor`: 사용자에게 보이는 동작 변화 없이 내부 구조를 바꾼다.
- `chore`: 도구, 운영, 문서, 유지보수 작업이다.

영역은 `frontend`·`backend`·`infra` 중 하나를 본문 첫 줄에 선언한다.
영역이 그 티켓이 갖춰야 할 증거를 정하며, 영역별 최소 증거는 [notion-ticket-contract.md](references/notion-ticket-contract.md)에 있다.
한 요청이 두 영역에 걸치면 증거 계약을 넓히지 말고 티켓을 둘로 쪼갠다.

페르소나는 `교직원`·`학생`·`관리자` 중 증거가 뒷받침하는 것만 고르고, 없으면 속성을 비우고 본문에 `미기록`을 쓴다.
재현 URL은 Notion에 두어도 안전하면 전체를 보존하고, 경로가 없는 작업에만 `해당 없음`을 쓴다.
증거에는 그것이 직접 실행한 관찰인지, 자동 테스트인지, 코드 검사인지, 미확인 보고인지 표시한다.

### 1.4 마감을 계산한다

Notion 생성일을 기준으로 계산하며 발행 다음 날이 첫 영업일이다.
월~금을 세고 신뢰할 수 있는 휴일 달력이 있을 때만 반영하며, 없으면 주말만 제외했다는 가정을 보고에 적는다.

관찰된 영향이 지지하는 가장 짧은 등급을 고른다.

- **1 영업일**: 보안·개인정보 노출, 데이터 손실·훼손, 권한 우회, 릴리스를 막는 핵심 흐름.
- **3 영업일**: 1일 등급이 아닌 재현 가능한 기능·API·인프라 결함.
- **5 영업일**: 릴리스를 막지 않는 UX·디자인·접근성·refactor·chore·개선 작업.

영향이 등급을 지지하지 못하면 추측하지 말고 묻는다.

### 1.5 증거를 동시에 모은다

캡처, 코드 앵커, 중복 조회는 본문으로 흘러 들어가지만 서로에게 입력을 주지 않는다.
그래서 순서대로 돌리지 않고 읽기 전용 subagent lane으로 동시에 던진다.
브라우저 lane은 하나만 띄운다 — 둘이 같은 tab을 잡으면 서로의 화면을 덮는다.

lane 구성, 캡처 절차, [`qa-dom-capture`](agents/qa-dom-capture.md)·[`qa-code-anchor`](agents/qa-code-anchor.md) agent, 보고를 받은 뒤 할 일은 [evidence-pipeline.md](references/evidence-pipeline.md)가 원본이다.
lane에는 판단이 아니라 확정된 대상을 넘기고, 돌아온 보고는 증거가 아니라 주장으로 받는다.
확인 가능한 경로, `경로:줄`, 행 id가 없는 항목은 본문에 옮기지 않고 `확인 필요`로 남긴다.

### 1.6 티켓 종류에 맞는 본문을 쓴다

본문 변형은 [notion-ticket-contract.md](references/notion-ticket-contract.md)에서 고른다.
속성은 색인과 배정을 위한 것이고 페이지 본문이 실행 계약이다.
사용자가 손으로 고친 참조 티켓을 지목하면 초안을 쓰기 전에 그 티켓을 다시 열어 섹션 순서, 문장 밀도, 어휘를 맞춘다.

모든 본문은 첫 heading 앞에 2~3줄의 여는 말로 시작한다.
이 화면에서 읽는 사람이 이미 겪고 있을 불편을 짚고, 이 티켓이 그중 무엇을 바꾸는지 말하고, 증거가 어디에 있는지 가리킨다.
어느 티켓에 붙여도 말이 되는 인사는 여는 말이 아니라 잉여다.

**기능 결함**이면 재현 중심 본문을 쓴다.
관찰한 동작만 절차로 쓰고 추정한 구현에서 절차를 역산하지 않는다.
실행 증거가 부족하면 지어내지 말고 `확인 필요`를 쓴다.

**UX·디자인 개선**이면 사람이 읽는 본문을 쓴다.
구현 항목을 나열하기 전에 현재 경험, 사용자 비용, 만들려는 결과를 먼저 설명한다.
그다음 UX 방향, 기대 흐름, 참고 UI, 최소 요구, 완료 조건, 작업 범위, 현재 화면을 그 순서로 쓴다.

참고 UI는 URL과 그 패턴이 보이는 요소의 캡처를 쌍으로 갖춘다 — 링크만 있는 레퍼런스는 채택하지 않는다.
반복 인용되는 제품은 [ux-reference-catalog.md](references/ux-reference-catalog.md)를 먼저 보고, 카탈로그에 있으면 URL과 경계를 다시 쓰지 말고 그 문서를 가리킨다.
후보는 실제 화면이 있는 둘에서 넷 정도만 보고, 흐름이 평범한 CRUD·파일·날짜 처리면 낯선 제품보다 익숙한 표준 패턴을 고른다.
후보마다 빌려올 점, 가져오지 않을 점, OSS Hub 경계를 적고, 승인은 하위 흐름별로 받는다.
승인 뒤에는 그 조합을 고정하고 탐색을 멈추며, 반려된 후보는 티켓에서 지운다.

`frontend` 티켓은 캡처보다 selector가 먼저다.
브라우저에서 대상 요소를 지목해 selector와 DOM path를 확정한 뒤 그 요소만 잘라 찍고, selector·DOM path·전체 URL·확인 시각을 이미지 옆에 남긴다.
화면 전체를 찍고 캡션으로 위치를 설명하는 방식은 이 계약을 만족하지 않으며, selector를 확정하지 못하면 캡처를 보류하고 `확인 필요`로 표시한다.

두 변형 모두 완료 조건은 지목된 페르소나가 관찰할 수 있는 형태로 쓰고, 가장 좁은 비목표를 명시한다.

### 1.7 쓰기 전에 다른 눈으로 검증한다

완성된 초안은 Notion에 쓰기 전에 [`qa-fact-checker`](agents/qa-fact-checker.md)에게 넘긴다.
주장을 만든 lane이 그 주장을 통과시키지 않는다 — 자기 초안을 검증하면 초안의 전제를 그대로 물려받는다.
`REFUTED`가 남아 있으면 그 문장을 고치기 전에 발행하지 않고, `UNVERIFIED`는 `확인 필요`로 본문에 남긴다.

제목, 작업 유형, 페르소나, 마감 등급, 본문 사실, 최소 요구, 완료 조건, 금지 범위가 서로 어긋나지 않는지 본다.
쓸 표면, 담당자, 마감 등급, 공개 안전 경계가 모호하면 초안을 먼저 보여 준다.

### 1.8 쓰고 나서 다시 읽어 맞춘다

기본 `QA 티켓` 템플릿으로 행을 만든다.
`상태`는 `신규`, `완료 여부`는 해제, 자동 요청자·요청일은 유지, 담당자는 0명 또는 1명이다.
지원되는 속성 값만 채우고 서술은 본문에 둔다.

쓴 뒤에 저장된 페이지를 다시 가져와 제목, 작업 유형, 페르소나, 마감, 담당자 수, 해제된 완료 여부, URL, 증거, 필요한 본문 섹션이 전부 맞는지 확인한다.
브라우저로 편집했다면 구조를 바꿀 때마다 페이지를 다시 읽는다 — 렌더된 블록 참조는 쉽게 낡는다.
기존 자리표시자는 렌더된 블록 전체를 선택해 교체하고, 낡은 템플릿 옆에 본문을 하나 더 붙이지 않는다.
이미지가 있으면 페이지를 다시 열어 문서 끝에서 캡션과 렌더된 이미지를 둘 다 확인한다 — 업로드 자리표시자는 저장 증거가 아니다.

다시 읽은 기록이 초안과 맞을 때까지 이 쓰기는 끝나지 않은 것으로 본다.

## 2. 발행 — Notion 행을 GitHub Issue로 내보낸다

Notion은 증거의 원본이고 GitHub Issue는 실행 표면이다.
Issue는 Notion을 열지 않고도 실행 가능해야 하며, 동시에 공개 저장소에 들어가면 안 되는 것을 넘겨받지 않아야 한다.

절차, 본문 재작성 규칙, 캡처 반입 기준, Notion `GitHub Issue` 속성 되돌려 연결, 이미 배정된 행의 일괄 backfill은 [github-publication.md](references/github-publication.md)가 원본이다.

핵심만 옮기면 이렇다.

- 저장소의 [work-ticket 템플릿](../../.github/ISSUE_TEMPLATE/work-ticket.md) 섹션을 전부 채우고, 세 실행 계약 섹션(`최소 요구`·`완료 조건`·`절대 금지`)을 비우지 않는다.
- Notion 본문을 인용하지 않고 공개 표면을 위해 다시 쓴다. 사람은 GitHub @handle로만 부른다.
- OSS Hub 자체 화면의 요소 캡처는 개인정보 검사를 통과하면 Issue에 넣는다. 제3자 제품 캡처는 Notion에만 두고 공개 표면에는 URL만 남긴다.
- 발행 전에 초안 전문을 저장소 밖 임시 파일에 쓰고 그 텍스트 그대로 검사한다.

```bash
ISSUE_TEXT="$(cat <draft-file>)" bash scripts/check-public-safe.sh --text-only
```

- 만든 뒤 Issue를 다시 가져와 제목, 본문, label, 담당자, QA 번호 참조를 확인하고, 그 Issue URL을 Notion 행의 `GitHub Issue` 속성에 되돌려 쓴다.
- 되돌려 쓴 뒤 Notion 행을 다시 읽어 URL이 저장됐는지 확인한다. 연결되지 않은 Issue는 고아이며 두 원본이 서로를 모른다.

## 3. 수행 — Issue를 PR로 만든다

`oss-hub 티켓 #<번호> 진행해줘`를 받으면 그 Issue 본문이 작업 범위의 유일한 원본이다.
성공 기준은 PR이 티켓 계약이 요구한 것과 정확히 일치하고, 완료 조건의 모든 항목이 PR을 열기 전에 실증되며, 금지 경계 밖의 파일을 0건 건드리는 것이다.

절차, 계약 파싱, 선행 의존성과 순환 처리, 검증과 PR 흐름, 이스케이프 해치는 [execution-workflow.md](references/execution-workflow.md)가 원본이다.

## 4. 레거시 행 이관

원본 데이터베이스가 실데이터 금지 규칙 아래 있는지 확인한 뒤에 서술 필드를 읽거나 옮긴다.
정규화된 공개 안전 필드만 저장소 밖 승인된 임시 위치에 백업하고, 첨부·자격증명·개인정보·private 저장소 세부·무제한 원본 덤프는 내보내지 않는다.
금지된 값이 있는 행은 제외하고 멈춘 뒤 안전한 처리 경로를 요청한다 — 조용히 가리고 복사하지 않는다.

번호 있는 행, 중복, 빈 번호, 번호 없는 행, 원문 없음, 이미 이관됨을 센다.
제목 없는 행이나 번호 없는 행은 별도 승인 없이 바꾸지 않는다.
이미 이관된 행은 본문을 하나 더 붙이지 말고 건너뛴다.
안전이 확인된 행은 원문 문제 서술을 `문제와 영향`에 그대로 옮기고 옛 분류는 레거시 사실로 표시해 보존한다.

승인된 backfill에서는 보안·개인정보 범주를 1일, 기능·인프라 범주를 3일, UX·디자인 범주를 5일로 매핑하고, 범주가 빈 행은 승인된 기본값 3일을 쓰며 그 가정을 보고에 남긴다.
모든 대상 행을 다시 읽어 원문이 본문에 정확히 한 번 나타나고 계산된 마감이 맞는지 증명한다.
레거시 속성 삭제는 검증 보고가 끝난 뒤 명시적 승인을 받아야 한다.
한 행이라도 검증에 실패하면 모든 원본 속성을 보존하고 실패한 행과 복구 경로를 보고한다.

## 안티패턴

- Notion 행 없이 Issue부터 만든다 → 증거가 어디에도 남지 않는다. 1단계를 먼저 한다.
- Notion 본문을 GitHub Issue에 그대로 붙여넣는다 → 공개 표면을 위해 다시 쓴다. 사본은 원본이 고쳐질 때 갈라진다.
- Issue를 만들고 Notion에 URL을 안 쓴다 → 두 원본이 서로를 모르는 고아 Issue가 된다.
- UX 개선을 구현 체크리스트로 시작한다 → 현재 경험, 사용자 영향, 목표, 기대 흐름을 파일·API보다 먼저 쓴다.
- 참고 링크를 해석 없이 나열한다 → 레퍼런스마다 쓸모 있는 패턴과 제한된 OSS Hub 적용을 적는다.
- 승인 뒤에도 레퍼런스를 더 찾거나 반려된 후보를 남긴다 → 승인된 조합을 고정하고 나머지는 지운다.
- 사용자가 기존 티켓 URL을 줬는데 대체 행을 만든다 → 지목된 행을 고치고, 중복이 따로 있으면 별도로 보고하며, 승인 없이 지우지 않는다.
- 화면 전체를 찍고 캡션으로 대상을 설명한다 → selector를 먼저 확정하고 그 요소만 찍는다.
- 캡처·앵커·중복 조회를 한 줄로 순서대로 돌린다 → 입력을 공유하지 않으므로 동시 lane으로 띄운다.
- lane의 요약을 증거로 받는다 → 각 주장 뒤의 경로, `경로:줄`, 행 id를 요구한다.
- 이미지 자리표시자를 저장된 증거로 본다 → 페이지를 다시 열어 문서 끝의 캡션과 렌더된 이미지를 확인한다.
- AGENTS.md의 브랜치·커밋·보안 규칙을 이 스킬 안에 옮겨 적는다 → 원본과 갈라진다. 항상 AGENTS.md를 직접 읽는다.
- 최소 요구가 요구하지 않은 "개선"을 PR에 얹는다 → 빼고 별도 티켓으로 제안한다.
- 구동해보지 않고 완료 조건을 체크한다 → 먼저 실제로 돌린 뒤 체크한다.

## 완료 체크리스트

작성(1단계)에 해당하는 항목:

- [ ] 살아 있는 Notion schema와 기본 템플릿을 읽었다.
- [ ] 만들기 직전에 중복을 다시 조회했다.
- [ ] 증거 기반으로 본문 변형을 골랐고, 사용자가 지목한 참조 티켓이 있으면 다시 열었다.
- [ ] 모든 lane 주장이 확인 가능한 산출물을 달고 왔고, 없는 것은 `확인 필요`다.
- [ ] 별도 팩트 체크 통과했고 `REFUTED`가 남아 있지 않다.
- [ ] 화면 하나 또는 산출물 위치 하나와 논리 변경 하나만 다룬다.
- [ ] 본문이 이 화면의 불편을 짚는 2~3줄 여는 말로 시작한다.
- [ ] 영역을 하나 선언했고 영역별 최소 증거가 있다.
- [ ] 모든 `frontend` 캡처가 요소 단위이며 selector·DOM path·URL·확인 시각을 달고 있다.
- [ ] 모든 참고 UI에 캡처가 있고, 승인된 조합만 남아 있다.
- [ ] 작업 유형·페르소나·담당자 0~1명·마감이 증거로 뒷받침된다.
- [ ] 저장된 Notion 페이지를 다시 읽어 초안과 맞췄고, 이미지는 렌더된 상태로 확인했다.

발행(2단계)에 해당하는 항목:

- [ ] Issue가 템플릿의 모든 섹션을 채우고 Notion 없이 실행 가능하다.
- [ ] 세 실행 계약 섹션이 비어 있지 않다.
- [ ] 제3자 캡처가 공개 표면으로 넘어가지 않았고, 반입한 자체 화면 캡처는 개인정보 검사를 통과했다.
- [ ] 초안 전문으로 `ISSUE_TEXT` public-safe 검사를 통과했다.
- [ ] Issue URL을 Notion `GitHub Issue` 속성에 썼고 다시 읽어 확인했다.

수행(3단계)에 해당하는 항목:

- [ ] 세 계약 섹션을 읽었고 선행 의존성을 확인했다.
- [ ] 첫 수정 전에 루트와 관련 중첩 AGENTS.md를 읽었다.
- [ ] 금지 섹션 밖 파일을 0건 수정했다.
- [ ] 완료 조건 각 항목을 실제 증거로 실증했다.
- [ ] `bash scripts/check-public-safe.sh`를 PR 전에 실행했다.
- [ ] AGENTS.md가 정한 흐름대로 PR을 열고 보드 카드를 옮겼다.
