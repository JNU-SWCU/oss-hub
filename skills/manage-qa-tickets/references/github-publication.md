# 발행 계약 — Notion 행을 GitHub Issue로 내보낸다

Notion은 증거의 원본이고 GitHub Issue는 실행 표면이다.
같은 티켓이 두 곳에 있으므로 둘이 다르게 적히면 실행하는 사람은 어느 쪽이 계약인지 알 수 없다.
그래서 Issue는 Notion 본문의 사본이며, 발행 단계가 하는 일은 다시 쓰는 것이 아니라 그대로 옮기고 공개 표면에 넣으면 안 되는 것만 걸러내는 것이다.

## 언제 발행하나

새로 쓴 행은 작성이 끝나는 즉시 이어서 발행한다.
1단계의 재조회 검증이 통과하면 다시 묻지 않고 Issue를 만들고 URL을 되돌려 쓴다 — 티켓을 써 달라는 요청은 그 티켓을 실행 표면에 올려 달라는 요청이다.
발행되지 않은 행은 아무도 집을 수 없고, 발행을 다음 요청으로 미루면 그 요청은 대개 오지 않는다.

이어 붙이지 않는 경우는 셋뿐이다.

- 사용자가 초안만 보자고 했다 — 초안 요청은 Notion 쓰기 허가도 발행 허가도 아니다.
- 사용자가 이 행은 발행하지 말라고 했다.
- 행이 아래 발행 조건을 만족하지 못한다.

행이 아래를 전부 만족할 때 발행한다.

- 본문에 최소 요구, 완료 조건, 그리고 경계 서술이 있다 — 기능 결함 본문은 `절대 금지`, UX 본문은 `작업 범위`의 비변경 항목이 경계다.
- `상태`가 `거부됨`이 아니다.
- 아직 `GitHub Issue` 속성이 비어 있다 — 값이 있으면 이미 발행된 행이므로 새로 만들지 말고 그 Issue를 고친다.

`담당자`가 비어 있어도 발행할 수 있다.
담당자 없는 Issue는 아직 안 집은 일이지 발행하면 안 되는 일이 아니다.

이어 붙는 발행은 방금 이 대화에서 쓴 행에만 적용된다.
이미 있던 행을 지금 발행하는 것은 자동이 아니며 사용자가 지목한 행만 발행한다 — "이 테이블 좀 봐 줘"는 발행 허가가 아니다.

## 본문을 그대로 미러링한다

Issue 본문은 Notion 본문의 사본이다.
여는 말, 섹션 순서, heading, 문장, 체크박스, 목록을 그대로 옮기고 공개 표면을 위해 다시 쓰지 않는다.
재작성은 표면마다 다른 계약을 만들고, 그 차이는 티켓을 실행한 뒤 리뷰에서야 드러난다.

Issue 본문에 Notion에 없는 것을 넣는 자리는 둘뿐이다.

- 맨 앞에 저장소 [work-ticket 템플릿](../../../.github/ISSUE_TEMPLATE/work-ticket.md)의 `## 시작` 블록을 문구 그대로 둔다 — 실행 진입점이고 Notion 본문에는 없다.
- 맨 끝에 출처 한 줄을 남긴다 — `출처: QA<번호>`.

Notion 페이지 URL은 Issue에 넣지 않는다.
공개 Issue에서 열리지 않는 링크는 독자에게 막다른 길이고, 두 표면의 연결은 Notion 쪽 `GitHub Issue` 속성이 들고 있다.

미러링에서 바꾸는 내용은 아래 둘뿐이다.

- 공개 안전 검사에 걸린 문자열. 이때도 Issue에서만 고치지 않는다 — Notion 본문을 먼저 고치고 고친 본문을 다시 미러링한다. 한쪽만 고치면 사본이 갈라지고, Notion에 남은 문자열은 다음 발행에서 그대로 다시 나온다.
- 제3자 제품 캡처. 이미지는 반입하지 않고 그 자리에 URL과 패턴 서술만 남긴다([이미지 반입 기준](#이미지-반입-기준)).

Notion 본문에 없는 사실을 Issue에서 채워 넣지 않는다.
파일 경로, API 경로, 선행 의존성이 비어 있으면 그것은 발행 단계에서 보충할 정보가 아니라 1단계가 덜 끝났다는 신호다 — Notion 행을 먼저 보강하고 그 본문을 미러링한다.

세 실행 계약(최소 요구·완료 조건·경계) 중 하나라도 Notion 본문에 없으면 발행하지 않는다.
빈 경계는 "경계 없음"이 아니라 "미기록"이며, 경계 없는 티켓은 범위가 없는 티켓이다.

## 속성 매핑

| Notion | GitHub |
| --- | --- |
| `QA 항목` | 제목 `[P<등급>] <화면 이름>`. `QA<번호>.` 접두는 제목이 아니라 본문 끝 출처 줄이 들고 있다 |
| `마감` | 제목의 `[P<등급>]` — 1일=P0, 3일=P1, 5일=P2. 날짜 자체는 Issue에 복제하지 않는다 |
| `작업 유형` | label — `feat`·`fix`·`refactor`·`chore` 중 해당하는 것 (기본 `ticket` label과 함께) |
| `페르소나` | 본문에 이미 있다. 별도 label로 만들지 않는다 |
| `상태` | 복제하지 않는다. 발행 이후 진행 상태의 원본은 Issue와 프로젝트 보드다 |
| `완료 여부` | 복제하지 않는다. 사람이 배포 환경에서 확인한 뒤에만 Notion에서 체크한다 |

저장소에 없는 label을 만들지 않는다.
필요한 label이 없으면 `ticket`만 달고 보고한다.

## 담당자 매핑

Notion `담당자`는 Notion 계정이고 Issue assignee는 GitHub 계정이다.
둘은 자동으로 이어지지 않으므로 추측해서 매핑하지 않는다 — 잘못 배정된 티켓은 엉뚱한 사람의 할 일 목록에 들어가 조용히 방치된다.

확인된 매핑만 쓴다. 확인 경로는 하나다 — 사용자가 대화에서 알려주는 것.
한 번 확인된 매핑은 아래 표에 남기고 다음 발행부터는 다시 묻지 않는다.

### 확인된 매핑

| Notion `담당자` user ID | Issue assignee |
| --- | --- |
| `7e1375ef-01bc-420b-b968-3739d642279b` | `Geuin04` |
| `270d872b-594c-8148-ab62-000223e60a8b` | `jinsol1190-rgb` |
| `45b7b07b-6ede-403d-ae77-582d2c612fa9` | `Lumiere001` |

표의 왼쪽 칸은 실명이 아니라 Notion user ID다.
[보안 규칙](../../../docs/rules/security.md) deny-list 1번이 금지하는 것은 실명과 GitHub 핸들을 잇는 표이므로, 실명을 한 번도 적지 않는 이 표는 그 금지에 걸리지 않는다.
user ID는 해당 워크스페이스 밖에서는 아무 사람도 가리키지 않고, 워크스페이스 안에서는 이미 서로를 아는 사람들만 본다.
이 예외는 user ID에만 적용된다 — 이름, 이메일, 학번을 이 표나 다른 어디에도 덧붙이지 않는다.

`담당자`를 읽을 때 표시 이름이 아니라 user ID로 대조한다.
표시 이름은 사람이 바꿀 수 있고 동명이인에서 갈리지만 user ID는 계정을 따라간다.

표에 없는 user ID를 만나면 배정을 추측하지 않는다.
누구인지 사용자에게 묻고, 답을 받은 뒤에 배정하고, 같은 PR 또는 후속 PR로 이 표에 한 줄을 더한다.

`요청자`는 매핑 대상이 아니다. assignee는 `담당자`만 따라간다.

이미 발행된 Issue의 assignee를 매핑 근거로 삼지 않는다.
서로 다른 Notion 담당자의 행이 같은 GitHub 계정에 배정돼 있으면 그 배정은 담당자를 따라간 것이 아니라 발행자를 따라간 것이고, 그 위에서 추론한 매핑은 다음 티켓을 엉뚱한 사람에게 보낸다.

매핑을 확인할 수 없으면 assignee 없이 발행한다.
담당자 정보는 Notion 행이 이미 들고 있으므로 잃어버리는 것이 없고, 누구에게 배정해야 하는지는 보고에 남긴다.

## 이미지 반입 기준

미러링의 유일한 내용 예외가 이미지다. 캡처의 출처가 기준을 정한다.

- **OSS Hub 자체 화면**의 요소 캡처는 Issue에 넣는다. 고칠 사람이 무엇이 잘못됐는지 보는 것이 티켓의 절반이고, 우리 화면은 우리가 공개해도 되는 화면이다.
- **제3자 제품 캡처**는 Notion에만 둔다. 공개 표면에는 URL과 빌려올 패턴 서술만 남긴다 — 남의 제품 화면을 우리 공개 저장소에 재배포하지 않는다.

자체 화면 캡처라도 Issue에 넣기 전에 이미지 자체를 눈으로 확인한다.

- 실이름, 실제 이메일, 학번, 전화번호, 실제 업로드 파일명이 프레임 안에 있으면 넣지 않는다.
- 세션 토큰, 쿠키, 개발자 도구, 주소창의 인증 파라미터가 보이면 넣지 않는다.
- 그 요소만 잘려 있는지 본다 — 요소 캡처 계약은 발행 표면에서도 유지된다.

하나라도 걸리면 캡처를 반입하지 않고 Notion에 남긴 뒤 Issue에는 재현 경로만 쓴다.
가리고 넣는 것보다 안 넣는 편이 안전하다.

`gh`에는 이미지 업로드 API가 없다.
그래서 이미지는 GitHub 웹 편집기에 붙여 넣어 올리고, 그때 GitHub이 만들어 주는 첨부 URL을 본문에 쓴다.
이미지를 저장소에 커밋해 raw URL로 참조하지 않는다 — QA 캡처는 저장소 이력에 남을 산출물이 아니다.
브라우저 경로를 쓸 수 없으면 텍스트만으로 발행하고, 캡처는 Notion에 있으며 아직 반입되지 않았다고 보고에 남긴다.

Notion 본문이 이미지 아래에 달고 있던 selector, 전체 URL, 확인 시각 줄은 그대로 함께 옮긴다.
이미지 없이 캡션만 남기지 않는다.

## 발행 전 검사

초안 제목과 본문 전문을 저장소 밖 임시 파일에 쓰고, 그 텍스트 그대로 검사한다.

```bash
ISSUE_TEXT="$(cat <draft-file>)" bash scripts/check-public-safe.sh --text-only
```

요약본이나 일부만 검사하지 않는다 — 검사한 텍스트와 발행한 텍스트가 다르면 검사는 아무것도 보장하지 않는다.
검사가 실패하면 Notion 본문에서 걸린 문자열을 고치고, 고친 본문을 다시 가져와 다시 검사한다.

이 저장소의 CI에도 issue 본문을 검사하는 job이 있지만, 그때는 이미 공개된 뒤다.
발행 전 검사가 실제 방어선이다.

## Notion 되돌려 연결

Issue를 만든 뒤 다시 가져와 제목, 본문, label, assignee, `QA<번호>` 참조가 의도대로인지 확인한다.
본문은 Notion 본문과 대조해 섹션과 문장이 그대로인지 본다 — 미러링은 붙여 넣은 순간이 아니라 대조한 순간에 끝난다.

그다음 Issue URL을 Notion 행의 `GitHub Issue` 속성(URL 타입)에 쓴다.
속성이 아직 없으면 데이터소스에 추가한 뒤 쓴다.
연결되지 않은 Issue는 고아다 — 두 원본이 서로를 모르면 다음 사람이 같은 행으로 두 번째 Issue를 만든다.

쓴 뒤 Notion 행을 다시 읽어 URL이 저장됐는지 확인한다.
`상태`는 발행만으로 바꾸지 않는다 — 상태는 사람이 옮긴다.

## 이미 배정된 행 backfill

이미 담당자가 있고 Issue가 없는 행들을 한 번에 잇는 작업이다.

1. `GitHub Issue` 속성이 비어 있고 `상태`가 `거부됨`이 아닌 행을 전부 센다.
2. 그중 이미 GitHub에 대응 Issue가 있는 행을 먼저 찾는다 — 제목·경로·증상으로 대조하고, 있으면 새로 만들지 말고 그 URL을 연결만 한다.
3. 남은 행을 한 건씩 위 절차대로 발행한다. 한 번에 다 만들고 나중에 검증하지 않는다 — 검증 없이 쌓인 Issue는 되돌리기가 만드는 것보다 비싸다.
4. 행마다 발행 → 재조회 → Notion 연결 → 연결 재확인까지 끝낸 뒤 다음 행으로 간다.
5. 끝나면 발행한 수, 기존 Issue에 연결만 한 수, 담당자 매핑을 확인하지 못해 assignee 없이 나간 수, 건너뛴 행과 그 이유를 보고한다.

세 실행 계약을 담고 있지 않은 행은 발행하지 않고 건너뛴다.
근거 없는 행을 형식만 맞춰 발행하면 실행할 수 없는 Issue가 담당자에게 배정된다.
