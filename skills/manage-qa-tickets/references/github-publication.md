# 발행 계약 — 초안을 GitHub Issue로 만든다

QA·작업 티켓의 원본은 GitHub Issue 하나다.
작성 단계의 초안이 곧 발행할 본문이며, 다른 저장소로 미러링하지 않는다.
발행이 하는 일은 초안을 공개 안전 검사에 통과시킨 뒤 `gh issue create`로 만들고, 만든 Issue를 다시 읽어 맞추는 것이다.

## 언제 발행하나

검증을 통과한 초안은 작성이 끝나는 즉시 이어서 발행한다.
1단계의 재조회와 팩트 체크가 통과하면 다시 묻지 않고 Issue를 만든다.
티켓을 써 달라는 요청은 그 티켓을 실행 표면에 올려 달라는 요청이다.
발행되지 않은 초안은 아무도 집을 수 없고, 발행을 다음 요청으로 미루면 그 요청은 대개 오지 않는다.

이어 붙이지 않는 경우는 셋뿐이다.

- 사용자가 초안만 보자고 했다. 초안 요청은 발행 허가가 아니다.
- 사용자가 이 초안은 발행하지 말라고 했다.
- 초안이 아래 발행 조건을 만족하지 못한다.

초안이 아래를 전부 만족할 때 발행한다.

- 본문에 요구 범위(기능 결함은 `할 일`, UX는 `최소 요구`), 완료 조건, 경계 서술이 있다. 기능 결함 본문은 `하지 않을 것 (이 티켓의 경계)`, UX 본문은 `작업 범위`의 비변경 항목이 경계다.
- 같은 제목·경로·증상·역할의 열린 Issue나 닫힌 Issue가 없다. 있으면 새로 만들지 말고 그 Issue를 고치거나 참조한다.

담당자가 없어도 발행할 수 있다.
담당자 없는 Issue는 아직 안 집은 일이지 발행하면 안 되는 일이 아니다.

이어 붙는 발행은 방금 이 대화에서 쓴 초안에만 적용된다.
이미 있는 Issue를 지금 고치는 것은 자동이 아니며 사용자가 지목한 Issue만 고친다.

## 초안을 그대로 발행한다

Issue 본문은 저장소 밖에 둔 초안 파일의 사본이다.
여는 말, 섹션 순서, heading, 문장, 체크박스, 목록을 그대로 옮기고 발행 단계에서 다시 쓰지 않는다.
재작성은 초안과 발행본의 계약을 갈라 놓고, 그 차이는 티켓을 실행한 뒤 리뷰에서야 드러난다.

본문 맨 앞에는 저장소 [work-ticket 템플릿](../../../.github/ISSUE_TEMPLATE/work-ticket.md)의 `## 시작` 블록을 문구 그대로 둔다.
실행 진입점이고 초안의 문제 서술보다 앞에 온다.
`출처: QA<번호>` 꼬리표는 두지 않는다.
번호는 제목의 `QA<번호>`가 들고 있고, 본문에 같은 번호를 한 번 더 적으면 두 표면이 어긋날 자리가 생긴다.

발행 뒤 그 Issue에 남기는 진행·막힘 코멘트는 이 문서가 아니라 [write-github-comment](../../write-github-comment/SKILL.md)의 진행 템플릿을 쓴다.
PR이 Issue를 `Closes` 또는 `Refs`로 가리키면 GitHub가 링크를 만들므로, PR URL을 Issue 코멘트로 다시 남기지 않는다.

발행 전에 바꾸는 내용은 공개 안전 검사에 걸린 문자열뿐이다.
걸린 문자열은 초안 파일에서 고치고 같은 파일을 다시 검사한 뒤 그 파일로 발행한다.
Issue를 만든 뒤에만 고치면 검사한 텍스트와 공개된 텍스트가 달라진다.

초안에 없는 사실을 발행 단계에서 채워 넣지 않는다.
파일 경로, API 경로, 선행 의존성이 비어 있으면 그것은 발행 단계에서 보충할 정보가 아니라 1단계가 덜 끝났다는 신호다.
초안을 먼저 보강한 뒤 그 파일을 발행한다.

세 실행 계약(요구 범위·완료 조건·경계) 중 하나라도 초안에 없으면 발행하지 않는다.
빈 경계는 "경계 없음"이 아니라 "미기록"이며, 경계 없는 티켓은 범위가 없는 티켓이다.

## 제목·label·담당자·마감

제목은 [issue-ticket-contract.md](issue-ticket-contract.md)의 `QA<번호>. <명령형 할 일>`이다.
`[P1]` 같은 등급 접두가 있으면 번호 앞에 둔다.
증상은 제목이 아니라 본문 `문제`에 쓴다.

| 값 | Issue |
| --- | --- |
| 제목 | `QA<번호>. <명령형 할 일>` |
| 마감 | 본문 `## 우선순위와 기한`의 `마감:` 줄. 1 영업일=`P0`, 3 영업일=`P1`, 5 영업일=`P2` |
| 작업 유형 | 본문 한 줄 `작업 유형: feat\|fix\|refactor\|chore`. 그 이름의 label은 저장소에 없다 |
| 페르소나 | 본문 `페르소나` 줄. 별도 label로 만들지 않는다 |
| 진행 | Issue open/closed와 프로젝트 보드. 별도 상태 속성을 만들지 않는다 |

기본 label은 저장소에 있는 `ticket`이다.
2026-09-23 `gh label list --repo JNU-SWCU/oss-hub` 기준 저장소 label은 `bug`, `documentation`, `duplicate`, `enhancement`, `good first issue`, `help wanted`, `invalid`, `question`, `wontfix`, `ticket`이다.
없는 label을 만들지 않는다.
의미가 맞는 저장소 label만 추가하고, 없으면 `ticket`만 달고 보고한다.

담당자는 GitHub @handle 0명 또는 1명이다.
사용자는 핸들을 대화에서 알려 주고, 에이전트는 그 핸들만 `--assignee`에 넣는다.
표시 이름, 이메일, 다른 시스템 계정으로 핸들을 추측하지 않는다.
잘못 배정된 티켓은 엉뚱한 사람의 할 일 목록에 들어가 조용히 방치된다.
남을 담당자로 지정하려면 그 사람이 동의했다는 사실을 사용자가 이 대화에서 알려 주어야 한다.
근거가 없으면 assignee 없이 발행하고 누구에게 배정해야 하는지는 보고에 남긴다.
스스로를 지정하는 것은 언제나 가능하다.

## 이미지 반입 기준

OSS Hub 자체 화면의 요소 캡처는 Issue에 넣는다.
고칠 사람이 무엇이 잘못됐는지 보는 것이 티켓의 절반이고, 우리 화면은 우리가 공개해도 되는 화면이다.
제3자 제품 스크린샷은 어디에도 넣지 않는다.
패턴은 문장으로 적고 공개 URL만 남긴다.
남의 제품 화면을 우리 공개 저장소에 재배포하지 않는다.

자체 화면 캡처라도 Issue에 넣기 전에 이미지 자체를 눈으로 확인한다.

- 실이름, 실제 이메일, 학번, 전화번호, 실제 업로드 파일명이 프레임 안에 있으면 넣지 않는다.
- 세션 토큰, 쿠키, 개발자 도구, 주소창의 인증 파라미터가 보이면 넣지 않는다.
- 그 요소만 잘려 있는지 본다. 요소 캡처 계약은 발행 표면에서도 유지된다.

하나라도 걸리면 캡처를 넣지 않고 재현 경로만 쓴다.
가리고 넣는 것보다 안 넣는 편이 안전하다.

`gh`에는 이미지 업로드 API가 없다.
그래서 이미지는 GitHub 웹 편집기에 붙여 넣어 올리고, 그때 GitHub이 만들어 주는 첨부 URL을 본문에 쓴다.
이미지를 저장소에 커밋해 raw URL로 참조하지 않는다.
QA 캡처는 저장소 이력에 남을 산출물이 아니다.
브라우저 경로를 쓸 수 없으면 텍스트만으로 발행하고, 캡처가 아직 반입되지 않았다고 보고에 남긴다.
이미지 아래에 둔 selector, 전체 URL, 확인 시각 줄은 이미지와 함께 둔다.
이미지 없이 캡션만 남기지 않는다.

## 발행 전 검사

초안 제목과 본문 전문을 저장소 밖 임시 파일에 쓰고, 그 텍스트 그대로 검사한다.

```bash
ISSUE_TEXT="$(cat <draft-file>)" bash scripts/check-public-safe.sh --text-only
```

요약본이나 일부만 검사하지 않는다.
검사한 텍스트와 발행한 텍스트가 다르면 검사는 아무것도 보장하지 않는다.
검사가 실패하면 초안 파일에서 걸린 문자열을 고치고 같은 파일을 다시 검사한다.

이 저장소의 CI에도 issue 본문을 검사하는 job이 있지만, 그때는 이미 공개된 뒤다.
발행 전 검사가 실제 방어선이다.

## 만들고 다시 읽는다

검사는 통과한 초안 파일로만 만든다.
템플릿 앞부분의 `## 시작` 블록을 초안 앞에 붙인 파일이 본문 파일이다.

```bash
gh issue create --repo JNU-SWCU/oss-hub \
  --title "<QA<번호>. <명령형 할 일>>" \
  --body-file <body-file> \
  --label ticket \
  --assignee <github-handle>
```

담당자가 없으면 `--assignee`를 빼며, 추가 label이 있을 때만 `--label`을 반복한다.
만든 번호로 다시 읽는다.

```bash
gh issue view <number> --repo JNU-SWCU/oss-hub --json title,body,labels,assignees,state,url
```

제목, 본문 섹션, `ticket` label, assignee 수, 본문 `마감` 줄이 초안과 같은지 확인한다.
본문은 초안과 대조해 섹션과 문장이 그대로인지 본다.
발행은 명령을 친 순간이 아니라 다시 읽어 맞춘 순간에 끝난다.
맞지 않으면 그 Issue를 고치고 다시 읽는다.
새 Issue를 하나 더 만들어 덮지 않는다.
