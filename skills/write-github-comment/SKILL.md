# Write GitHub Comment

코멘트는 의사결정 지원 문서다.
PR 화면과 Issue 화면에는 이미 위젯이 많은 것을 말하고 있다 — checks 줄이 CI를, commit 목록이 무엇이 올라갔는지를, Files changed 탭이 어떤 파일을 고쳤는지를, label·assignee가 상태를 말한다.
코멘트가 할 일은 그 위젯이 말하지 못하는 것을 사람이 사람에게 말하는 것이다 — 왜 그런지, 무엇을 결정해야 하는지, 지금 화면이 실제로 어떻게 생겼는지.
형식이 눈앞에 없으면 지켜지지 않으므로 이 스킬이 네 코멘트의 템플릿을 들고 있다.

## 어느 코멘트인지 먼저 정한다

| 상황 | 템플릿 | 캡처 |
| --- | --- | --- |
| 리뷰어가 PR에 지적을 남긴다 | 지적 | frontend면 요소 캡처 필수 |
| 작성자가 리뷰 지적에 답한다 | 답글 | 고친 결과가 화면이면 After 요소 캡처 |
| 화면을 두고 다른 안을 제안한다 (PR·Issue 어디든) | UX 제안 | 현재 컴포넌트 요소 캡처 없이는 올리지 않는다 |
| Issue에 진행·PR 연결·막힘을 남긴다 | 진행 | 없음 |
| PR 본문 자체를 쓴다 | 이 스킬이 아니라 [`submit-pr-evidence`](../submit-pr-evidence/SKILL.md) | — |
| 티켓 본문을 쓴다 | 이 스킬이 아니라 [`manage-qa-tickets`](../manage-qa-tickets/SKILL.md) | — |

템플릿 원본은 [`references/comment-templates.md`](references/comment-templates.md)에 있다.
아래는 각 템플릿을 언제 쓰는지와 핵심 규칙만 두고, 채워 넣을 본문 블록은 그 파일에 둔다.

## 공통 원칙

### 초록불이 말해 주는 것은 쓰지 않고, 초록불이 감추는 것을 쓴다

PR 페이지도 화면이고, 그 화면에는 이미 위젯이 붙어 있다.
checks 줄이 CI와 테스트 결과를 말하고, commit 목록이 무엇이 올라갔는지 말하고, Files changed 탭이 어떤 파일을 고쳤는지 말한다.
답글에 그것을 문장으로 다시 적는 것은 [AP-19 위젯이 이미 말한 것](../submit-pr-evidence/references/ux-antipatterns.md#ap-19-위젯이-이미-말한-것--heuristic-4-일관성과-표준)을 PR 표면에서 되풀이하는 일이다.
리뷰어는 자기가 방금 본 것을 한 번 더 읽게 되고, 그 문단들 사이에서 정작 자기가 받아야 할 답을 찾지 못한다.

**초록불이 말해 주는 것은 쓰지 않고, 초록불이 감추는 것을 쓴다.**

답글에 쓰지 않는 것 — 전부 PR 화면이 이미 말하고 있다.

- `CI·public-safe·commitlint가 통과했습니다` — checks 줄이 lane 이름과 초록불로 말한다.
- `전체 프런트엔드 3,533개 테스트가 통과했습니다` — 이 수치는 checks 줄이 아니라 **PR 본문 `## 검증` 절**이 말한다. checks 줄은 lane이 초록이라는 것만 말하고 개수는 말하지 않는다([`submit-pr-evidence` 절차 7단계](../submit-pr-evidence/SKILL.md#절차)가 개수를 요구하는 이유가 그것이다) — 그래서 지우는 것이 아니라 본문 한 자리에 두고 답글에서 되풀이하지 않는 것이다.
- `후속 커밋은 <sha1>, <sha2>입니다` — 커밋 목록이 말한다. 다만 **어느 지적을 어느 커밋에서 고쳤는지**는 커밋 목록이 말하지 않으므로, 지적에 답하며 다는 `3번은 <commit 7자>에서 고쳤어`는 잉여가 아니라 답 자체다.
- `병합·배포는 하지 않았습니다` — 열려 있는 PR은 병합되지 않았다는 것을 스스로 보여 준다. 이 줄이 지우는 것은 **위젯이 이미 보여 주는 상태**뿐이다 — 「보류했다」·「승인을 기다린다」·「후속 티켓은 아직 없다」는 어느 위젯도 보여 주지 않으므로 그대로 쓴다.

수치가 쓸모없어진 것이 아니라 **자리가 하나뿐인 것이다.**
실행된 suite·test 개수는 PR 본문 `## 검증` 절에 남기고, 답글은 필요하면 그 절을 가리키기만 한다.

`## 검증` 절 갱신 규칙은 [리뷰 답글 작성 원칙](../submit-pr-evidence/SKILL.md#리뷰-답글-작성-원칙)이 원본이다 — 갱신하지 않으면 재검증 수치는 답글에도 본문에도 남지 않는다.

답글에 쓰는 것.

- **지적 한 건에 대한 답** — 고쳤다 / 안 고쳤다와 그 이유 / 판단을 기다린다 중 하나로 끝낸다. 리뷰어가 매긴 번호를 그대로 받아서 답해야 어느 지적의 답인지 세지 않아도 된다.
- **초록불이 감추는 것** — 한 번 실패했다가 재실행으로 통과한 검사, 원인을 모른 채 넘어간 것, 판단을 기다리느라 보류한 항목.
  - **browser E2E는 여기에 속한다.** `pnpm --filter frontend e2e`는 CI lane이 아니라 로컬 수동 게이트다([`.github/workflows/ci.yml:321`](https://github.com/JNU-SWCU/oss-hub/blob/main/.github/workflows/ci.yml#L321), [AGENTS.md](../../AGENTS.md)) — 돌렸다는 사실을 어떤 위젯도 표시하지 않으므로 답글에 쓰지 않으면 아무 데도 남지 않는다.
  - checks 줄이 이것들을 초록으로 덮어 버리므로, 사람이 답글에 쓰지 않으면 아무 데도 남지 않는다.
  - 다만 **돌리지 못한 검증**의 자리는 답글이 아니라 본문이다 — [돌리지 못한 검증은 본문 `## 검증`에 적는다](../submit-pr-evidence/SKILL.md#리뷰어에게-의미-없는-로컬-환경-잡음을-본문에-넣지-않는다)를 따른다.
- **리뷰어가 다음에 할 행동** — 무엇을 봐 달라는 것인지, 무엇을 결정해 달라는 것인지.

세 줄로 끝나면 세 줄로 끝낸다.
답글의 길이는 성실함의 증거가 아니다 — 리뷰어가 답을 찾는 데 드는 시간이다.

### 리뷰어가 매긴 번호를 그대로 받는다

답글에서 새로 번호를 매기면 어느 지적의 답인지 리뷰어가 다시 세야 한다.
리뷰어가 쓴 번호를 그대로 받아 쓰면 그 수고가 사라진다.

### 한 코멘트가 한 결정을 요구한다

두 개 이상의 판단거리가 한 코멘트에 섞이면 어느 것에 반응해야 하는지 흐려진다.
번호 목록으로 갈라 각 항목이 「고쳤다 / 안 고쳤다+이유 / 판단 부탁」 중 하나로 끝나게 한다.

### 화면 이야기는 화면을 보여 주며 한다

"이 부분이 이상하다"를 글로만 설명하면 읽는 사람이 화면을 열어 다시 찾아야 한다.
frontend 지적·제안은 그 컴포넌트의 요소 캡처(selector·URL·viewport 캡션)를 붙인다.
캡처 절차는 [`manage-qa-tickets/agents/qa-dom-capture.md`](../manage-qa-tickets/agents/qa-dom-capture.md)가 원본이고, 로그인 뒤 화면은 [`submit-pr-evidence/references/evidence-harness.md`](../submit-pr-evidence/references/evidence-harness.md)의 하네스로 띄운다.
이미지 업로드는 [`submit-pr-evidence/references/frontend-capture.md`](../submit-pr-evidence/references/frontend-capture.md#이미-발행된-release-에-에셋으로-올린다)(release asset `--clobber`)을 따른다 — `gh release create`는 절대 쓰지 않는다.

### 제안은 「지금 이렇게 생겼는데, 이게 낫지 않나?」 꼴이다

순서는 현재 캡처 → 지금 컴포넌트가 하는 말/일 → 제안하는 말/일 → 왜(AP-번호 또는 사용자 비용 한 문장) → 결정 부탁이다.
대안 mockup은 있으면 좋지만 없어도 된다. 있으면 「스케치」라고 표시한다 — 현재 캡처는 증거지만 제안 그림은 증거가 아니다.

### 티켓 범위 밖 제안은 코멘트로 끝내지 않고 티켓으로 간다

코멘트는 잊히고 티켓은 남는다.
「이건 이 PR 범위 밖이라 티켓으로 올릴게」 한 줄로 끝내고 [`manage-qa-tickets`](../manage-qa-tickets/SKILL.md)로 넘긴다.

### 말투는 쓰는 사람의 말투다

작성자가 반말을 쓰면 반말, 존댓말이면 존댓말이다.
에이전트 문체(「~하였습니다」「~을 확인하였습니다」)로 다듬지 않는다 — 다듬는 순간 누가 쓴 말인지가 코멘트에서 사라진다.
길이는 성실함의 증거가 아니다 — 세 줄로 끝나면 세 줄로 끝낸다.

### 가독성 형식을 지킨다

가독성 규칙의 원본은 [readability.md](../submit-pr-evidence/references/readability.md) 하나다 — 여기 다시 옮겨 적지 않는다.

### 공개 표면이다

실명·개인정보·실데이터·로컬 경로를 넣지 않는다. 사람은 `@handle`로만 쓴다.
올리기 전에 반드시 검사한다.

```bash
ISSUE_TEXT="$(cat <draft>)" bash scripts/check-public-safe.sh --text-only
```

## 절차

1. [위 표](#어느-코멘트인지-먼저-정한다)에서 어느 코멘트인지 정한다.
2. 답글이면 리뷰 지적을 번호별로 다시 읽는다 — 답하지 않은 번호가 있으면 그 답글은 미완이다.
3. 화면 이야기가 있으면 캡처를 먼저 만든다 — 요소 단위, selector 캡션, release asset 업로드, `curl -sIL … -w "%{http_code}"`로 200 확인까지 마친다.
4. 초안을 저장소 밖(scratchpad)에 파일로 쓴다 — 해당 템플릿을 열어 놓고 빈칸을 채운다.
5. `--text-only` public-safe 검사를 통과시킨다.
6. 「지우기」 패스를 한다 — 위젯이 이미 말하는 문장(초록불, 커밋 해시 나열, 병합 안 했다, 파일 목록)을 지운다. 지운 뒤 남는 것이 결정·이유·다음 행동이 아니면 다시 쓴다.
7. 올린다 — `gh pr comment <n> --body-file <draft>` / `gh issue comment <n> --body-file <draft>` / `gh pr review <n> --comment --body-file <draft>`. inline `--body "…"`는 쓰지 않는다 — 초안 파일이 검사 대상이기 때문이다.
8. 올린 코멘트를 브라우저나 `gh … --comments`로 다시 열어 이미지가 렌더됐는지 확인한다. 깨진 이미지는 없는 이미지다.

## 하지 않는 것

- CI·테스트 개수·lint 통과를 답글에 쓴다 → 본문 `## 검증`이 그 자리다.
- 화면을 글로만 설명한다 → 요소 캡처.
- 전체 화면을 찍고 캡션으로 위치를 설명한다 → selector 확정 후 그 요소만.
- 지적 열 개에 문단 하나로 답한다 → 번호별로.
- 제안만 하고 결정을 묻지 않는다 → 마지막 줄은 항상 「결정 부탁: …」 또는 「내가 이렇게 할게 — 아니면 말해줘」.
- 범위 밖 제안을 코멘트에 쌓는다 → 티켓.
- `--body "…"`로 바로 올린다 → 파일 초안 + 검사.
- 실명·「~님」 호칭에 실명을 쓴다 → `@handle`.

## 완료 체크리스트

- [ ] 어느 템플릿인지 정했고 그 템플릿의 자리를 다 채웠거나 비운 이유를 적었다.
- [ ] 리뷰어가 매긴 번호마다 답이 하나씩 있다 (답글일 때).
- [ ] 화면 이야기에는 요소 캡처가 있고 캡션에 selector·URL·viewport가 있다.
- [ ] 위젯이 이미 말하는 문장이 없다.
- [ ] 마지막 줄이 읽는 사람의 다음 행동을 말한다.
- [ ] 초안 파일로 public-safe `--text-only`를 통과했다.
- [ ] 올린 뒤 다시 열어 이미지 렌더를 확인했다.
- [ ] readability.md의 첫 화면 규칙을 통과했다 — 첫 줄이 결론이고 첫 15줄 안에 이미지 또는 다음 행동이 있다.
