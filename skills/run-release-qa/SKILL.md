# Run release QA

릴리스 후보를 고정한 뒤, 선언한 범위만큼만 기존 시나리오와 기록으로 출시 판정을 남긴다.
새 테스트 체계나 문서 체계를 만들지 않는다.

## Output contract

산출물은 exact SHA(알 수 없으면 `미기록`), 선언한 범위, 사용한 출처, 없는 출처, 출시 판정이다.
report-only는 설치·기동·스위트·시나리오 준비를 하지 않고, 없는 기록을 `확인 필요`로 남긴다.
전수 재실행은 사용자 명시 승인이 없으면 시작하지 않는다.
제품 코드·데이터·Issue·PR·Notion은 승인 없이 바꾸지 않는다.

## 범위를 먼저 고른다

환경 준비와 실행 레인 A–C보다 먼저, 아래 중 **하나만** 선언한다.
선언 전에는 `pnpm` 스위트, Docker, Playwright, 로컬 스택, 시나리오 준비, 플러그인 설치를 시작하지 않는다.

| 범위 | 하는 일 | 하지 않는 일 | 허가 |
| --- | --- | --- | --- |
| `report-only` (`재실행 안 함`, 기본) | 이미 있는 Notion·Issue·CI·이전 증거만 읽는다. 없는 출처는 `확인 필요`로 적는다. | 도구 설치, 서비스 기동, 스위트 실행, 전체 시나리오 준비, 화면 캡처 촬영 | 요청만으로 충분 |
| `recheck` (`기존 항목 재검증`) | 사용자가 지정한 QA 번호·URL만 재현한다. | 지정 밖 전수, 무단 Notion/Issue 쓰기 | 대상 목록이 있어야 함 |
| `delta` | 후보 SHA가 기준 커밋 이후로 움직인 **변경 경로만** 검증한다. | 무관한 경로 전수 | 기준 SHA가 있어야 함 |
| `full` (`전수 재실행`) | 시나리오 원본의 출시 핵심 경로를 다시 돈다. | 승인 없는 데이터·Issue·PR·Notion 변이 | **사용자 명시 승인 후에만** |

기존 행과 제목·증상·route·역할이 실질 동일하면 **알려진 문제**다. 새 발견으로 등록하지 않고 기존 URL·번호만 인용한다.

## 시작 전 경계

1. 공개 가능 범위는 `docs/rules/security.md`다. 실데이터·개인정보가 보이는 화면은 찍지 않는다.
2. 사용자 승인 없이 제품 코드, 운영 데이터, Issue, PR, Notion 상태를 수정하지 않는다.
3. QA 중에는 결함을 고치지 않는다. 수정 범위는 따로 승인한다.
4. 실행 범위(`recheck`·`delta`·`full`)만 루트·대상 경로 `AGENTS.md`, `docs/rules/local-dev.md`, `references/qa-scenarios.md`를 읽는다. report-only는 그 준비를 요구하지 않는다.
5. 제품 QA 발견 목록의 SSOT는 Notion `🐞 QA 요청`이다. 읽을 수 없으면 설치하지 말고 `확인 필요`로 남긴다.

## 0. 기록 조회

범위를 선언한 뒤에 읽을 수 있는 출처만 연다.

- Notion `🐞 QA 요청`: `QA 항목`, `문제 내용`, `Front URL`, `확인 역할`, `분류 영역`, `상태`, `수정 여부`
- 열린 GitHub Issue, 최근 CI 기록, 이미 있는 로컬 증거 파일

없는 출처는 만들지 않고 보고에 `확인 필요`로 적는다.
report-only는 여기서 판정에 필요한 읽기를 끝내고 §2·§3·레인 A–C로 가지 않는다.

## 1. 후보 고정

1. 지정된 branch·commit이 있으면 그 exact SHA를 기록한다. 없으면 이미 있는 git/CI 기록의 SHA를 쓰고, 그것도 없으면 `미기록`이다.
2. report-only는 원격 main을 갱신하거나 worktree를 새로 만들지 않는다.
3. 실행 범위만, 공유 checkout을 보존한 채 필요하면 별도 worktree에서 후보 SHA를 검사한다.
4. 시작 시각, 후보 SHA, base SHA, 작업 트리 상태, 범위 선언을 첫 줄에 남긴다.
5. QA 도중 main이 움직이면 drift로 보고하고 재실행은 사용자에게 맡긴다.

## 2. 최소 환경 준비

`recheck`·`delta`·`full`만 이 절을 수행한다. report-only는 건너뛴다.

1. 기존 `package.json` script에서 lint, typecheck, test, build, local 실행 명령을 찾는다.
2. 이미 있는 도구와 fixture만 쓴다. 한 번의 QA를 위해 새 프레임워크를 만들지 않는다.
3. raw 로그와 스크린샷은 저장소 밖 임시 또는 승인된 경로에 둔다.
4. 각 명령의 시작·종료 시각, exit code, 실패한 suite를 기록한다. 성공 요약만으로 실패 로그를 덮지 않는다.

## 3. 시나리오 선택

실행 범위만 `references/qa-scenarios.md`의 W·ST·PM·AS군에서 고른다.
report-only는 시나리오 준비를 하지 않는다.

- 역할: 비로그인, 역할 미선택, 학생, 팀장·팀원, 교직원, 관리자, 비활성 계정
- 흐름: 공개 조회, 가입·동의, 역할 요청, 프로그램, 신청, 저장소, 제출·검토, 관리자 기능
- 상태: 빈 값, 정상, 권한 없음, 미존재, 마감 경계, 중복, stale, 재시도, 최종 실패
- 화면: 320, 375, 768, 1280, 1440px와 키보드 전용 조작
- 계약: 성공, 400, 401, 403, 존재 은닉 404, 5xx, HTTP 200과 빈 본문 또는 null

비가역 전이는 시나리오 문서의 권장 순서를 따른다.
핵심 사슬 `W2 → W4 → W5 → W6 → W7 → W8 → W9`는 가능한 한 같은 fixture에서 이어서 확인한다.

## 4. 실행 순서

report-only는 레인 A–C를 실행하지 않는다. 기록 대조만 §4.D의 읽기 항목으로 한다.

### A. 정적·자동 검증

1. 선언한 QA 범위에 필요한 기존 검증을 [경로별 검증 규칙](../../docs/rules/ci-path-verification.md)에 따라 선택해 실행한다.
2. 실패와 경고를 분리한다. 테스트가 통과해도 반복 경고나 비결정적 신호는 별도 항목으로 기록한다.
3. 권한 검사, null 처리, 날짜 경계, 캐시, 공개 응답 allowlist, 비동기 최종 실패를 코드에서 교차 확인한다.

### B. API·권한 검증

1. PM군의 공개 200, 보호 401, 역할별 403, 존재 은닉 404 계약을 확인한다.
2. 보호 응답의 민감 필드와 `Cache-Control`을 확인한다.
3. 화면 문서가 200이어도 API가 데이터를 차단하는 구조인지 구분해 기록한다.
4. source finding과 실행 재현을 같은 수준으로 쓰지 않는다. 재현하지 못했다면 그 사실을 명시한다.

### C. 화면·상호작용 검증

1. 역할별 주요 route를 직접 연다. 목록에서 상세로 가는 흐름과 상세 URL 직접 진입을 모두 확인한다.
2. 좁은 화면의 잘림, 가로 스크롤, 한글 줄바꿈, 고정 버튼 도달 가능성을 확인한다.
3. 키보드 초점, Tab 순서, Escape 닫기, 창을 닫은 뒤 초점 복원을 확인한다.
4. 콘솔 오류, 중복 요청, 404·5xx 네트워크 요청을 화면 결과와 함께 묶는다.

### D. 전체 흐름·기존 발견 대조

1. 선언한 범위 안에서만 W군 핵심 사슬과 비동기 AS군을 실행한다. report-only면 시나리오 실행을 건너뛴다.
2. 읽을 수 있는 Notion `QA 요청`과 열린 GitHub Issue로 알려진 문제·회귀·실행 공백을 나눈다.
3. Issue·Notion 행을 닫거나 수정하지 않는다. 쓰기는 사용자가 명시한 경우에만 한다.

## 5. 증거 기록

각 발견 항목에 아래 정보만 남긴다.

- 후보 SHA와 실행 환경. report-only면 읽은 출처와 읽지 못한 출처
- 역할, route 또는 API, 사전 상태
- 재현 단계. 재현하지 않았으면 그 사실
- 실제 결과와 기대 결과
- 영향과 심각도
- 로그·응답·스크린샷 참조
- 실행 재현, 자동 테스트, 코드 점검, 기록 대조 중 어떤 근거인지

스크린샷은 식별 정보와 실데이터를 제거한 뒤 사용한다.
파일명은 `qa-id-role-route-viewport.png`처럼 재현 조건을 드러내고 개인 머신 경로는 문서에 쓰지 않는다.

## 6. Notion에 적을 때

사용자가 Notion 기록을 요청한 경우에만 작성한다.
토스의 라이팅 원칙 중 명확성, 간결성, 쉬운 말, 존중을 QA 문장에 적용한다.
report-only는 요청이 없으면 행을 만들지 않는다.

### 6.1 중복 등록 금지 (작성 직전 필수)

새 행을 만들기 전에 `QA 요청` DB를 다시 조회하고, 아래 중 **하나라도** 기존 행과 맞으면 생성하지 않는다. 기존 행 URL만 보고한다.

- 제목 핵심 구문이 같거나 한쪽이 다른 쪽을 포함
- 같은 `Front URL`(path 기준) + 같은 `확인 역할` + 같은 증상 요지
- `문제 내용`의 핵심 문장(실패 현상·route·역할)이 실질 동일
- 본문에 적힌 기준 SHA·회차와 같은 관찰을 다시 적는 경우

전수 QA 결과를 한 번에 대량 재적재하지 않는다. 신규로 판정된 항목만, 요청 범위 안에서 1건씩 추가한다.

### 6.2 문장

- 제목은 `조건에서 관찰된 문제` 순서로 쓴다.
- 본문은 관찰 결과, 기대 동작, 검증 기준을 2~4문장으로 쓴다.
- 한 문장에는 한 메시지만 담는다.
- `stub`, `seam`, `provision` 같은 용어는 재현에 꼭 필요하지 않으면 쉬운 한국어로 바꾼다.
- 확인하지 않은 영향은 단정하지 않는다.
- 군더더기, 감탄, 압박, 해결책 추측은 뺀다.
- 기존 상태, 담당자, 체크값은 요청 없이 바꾸지 않는다.

작성 뒤 대상 수, 제목 중복, 빈 본문, 상태 변경, 스크린샷 첨부 수를 다시 조회해 검증한다.
Notion 본문이나 비공개 링크를 저장소 문서에 복사하지 않는다.

## 7. 출시 판정

아래 셋 중 하나로 끝낸다.

- `RELEASE READY`: 출시 핵심 흐름이 통과했고 알려진 잔여 위험이 출시를 막지 않는다.
- `RELEASE BLOCKED`: 사용자가 일을 끝낼 수 없거나, 데이터·권한·개인정보가 위험하거나, 핵심 실패가 조용히 숨는다.
- `QA INCOMPLETE`: 환경·권한·fixture·기록이 부족해 핵심 경로를 검증하지 못했다. report-only에서 출처가 비면 이 판정이다.

최종 보고에는 exact SHA 또는 `미기록`, 선언한 범위, 통과·실패·미실행 수, blocker, 기존 Issue와의 관계, 증거 위치, 없는 출처를 적는다.
main이 이후 이동했다면 현재 SHA와의 차이를 한 줄로 알리고 결과가 고정 후보에만 유효하다고 명시한다.

- [ ] full이면 사용자 명시 승인을 받은 뒤에만 전수를 돌렸다.
