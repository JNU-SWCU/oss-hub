# Run release QA

oss-hub의 릴리스 후보를 움직이지 않는 기준점으로 고정하고, 기존 시나리오 원본을 따라 코드와 실제 동작을 함께 검증한다.
필요한 증거만 남기고 새 테스트 체계나 문서 체계를 만들지 않는다.

## 시작 전 경계

1. 루트 `AGENTS.md`와 점검 대상 경로의 중첩 `AGENTS.md`를 먼저 읽는다.
2. `references/qa-scenarios.md`를 시나리오 원본으로 사용한다.
3. 로컬 실행 방식은 `docs/rules/local-dev.md`, 공개 가능 범위는 `docs/rules/security.md`를 따른다.
4. 사용자 승인 없이 제품 코드, 데이터, Issue, PR, Notion 상태를 수정하지 않는다.
5. QA 중에는 결함을 고치지 않는다. 후보를 그대로 관찰한 뒤 수정 범위는 사용자와 따로 정한다.
6. 실데이터와 개인정보가 보이는 화면은 촬영하거나 저장소에 넣지 않는다. 합성 fixture만 사용한다.
7. **제품 QA 발견 목록의 SSOT는 Notion `🐞 QA 요청`이다.** 시나리오 실행·Issue 대조보다 먼저 이 DB를 조회한다. 이미 올라간 증상을 전수 재실행하거나 같은 행을 다시 만들지 않는다.

## 0. Notion QA 선조회 (필수)

시나리오를 돌리기 전에 Notion `QA 요청` DB를 읽고 작업 범위를 선언한다.

- DB: Notion `🐞 QA 요청` (JNU OSS Platform 하위). 워크스페이스 검색어 `QA 요청`으로 연다.
- 조회 항목: `QA 항목` 제목, `문제 내용`, `Front URL`, `확인 역할`, `분류 영역`, `상태`, `수정 여부`
- 범위는 아래 중 **하나만** 선언한 뒤 그 범위만 실행한다.
  - `재실행 안 함` — 기존 목록·CI 증거로 판정 요약만 (기본)
  - `기존 항목 재검증` — 사용자가 지정한 QA 번호·URL만 재현
  - `delta only` — 후보 SHA가 Notion 항목 기준 커밋 이후로 움직인 **변경 경로만**
  - `전수 재실행` — **사용자 명시 승인 후에만** 허용
- 기존 행과 제목·증상·route·역할이 실질 동일하면 **알려진 문제**로 분류하고 새 발견으로 보고·등록하지 않는다. 기존 행 URL·번호만 인용한다.
- 이 절을 건너뛰고 전수 탐색을 시작하지 않는다.

## 1. 후보 고정

1. 사용자가 지정한 branch 또는 commit을 확인한다. "최신 main"이면 원격 main을 갱신한 뒤 exact SHA를 기록한다.
2. 공유 checkout의 변경을 보존한다. 필요하면 별도 worktree에서 후보 SHA를 검사한다.
3. 시작 시각, 후보 SHA, base SHA, 작업 트리 상태, **§0 범위 선언**을 증거 기록의 첫 줄에 남긴다.
4. QA 도중 main이 움직여도 결과를 섞지 않는다. 새 SHA는 drift로 보고하고 재실행 여부를 사용자에게 맡긴다.

## 2. 최소 환경 준비

1. `package.json`과 각 앱의 기존 script에서 lint, typecheck, test, build, local 실행 명령을 찾는다.
2. 이미 있는 도구와 fixture를 우선 사용한다. 한 번의 QA를 위해 새 프레임워크나 범용 추상화를 만들지 않는다.
3. raw 로그와 스크린샷은 저장소 밖의 임시 또는 사용자 승인 경로에 둔다.
4. 각 명령의 시작·종료 시각, exit code, 실패한 suite를 기록한다. 성공 요약만으로 실패 로그를 덮지 않는다.

## 3. 시나리오 선택

`references/qa-scenarios.md`의 W·ST·PM·AS군에서 후보에 해당하는 항목을 고른다.
모든 조합을 무작정 곱하지 말고 아래 축으로 출시 핵심 경로와 위험 경계를 우선한다.

- 역할: 비로그인, 역할 미선택, 학생, 팀장·팀원, 교직원, 관리자, 비활성 계정
- 흐름: 공개 조회, 가입·동의, 역할 요청, 프로그램, 신청, 저장소, 제출·검토, 관리자 기능
- 상태: 빈 값, 정상, 권한 없음, 미존재, 마감 경계, 중복, stale, 재시도, 최종 실패
- 화면: 320, 375, 768, 1280, 1440px와 키보드 전용 조작
- 계약: 성공, 400, 401, 403, 존재 은닉 404, 5xx, HTTP 200과 빈 본문 또는 null

비가역 전이는 시나리오 문서의 권장 순서를 따른다.
핵심 사슬 `W2 → W4 → W5 → W6 → W7 → W8 → W9`는 가능한 한 같은 fixture에서 이어서 확인한다.

## 4. 실행 순서

### A. 정적·자동 검증

1. 기존 lint, typecheck, unit, integration, build를 실행한다.
2. 실패와 경고를 분리한다. 테스트가 통과해도 반복 경고나 비결정적 신호는 별도 항목으로 기록한다.
3. 권한 검사, null 처리, 날짜 경계, 캐시, 공개 응답 allowlist, 비동기 최종 실패를 코드에서 교차 확인한다.

### B. API·권한 검증

1. PM군의 공개 200, 보호 401, 역할별 403, 존재 은닉 404 계약을 확인한다.
2. 보호 응답의 민감 필드와 `Cache-Control`을 확인한다.
3. 화면 문서가 200이어도 API가 데이터를 차단하는 구조인지 구분해 기록한다.
4. source finding과 실행 재현을 같은 수준으로 표현하지 않는다. 재현하지 못했다면 그 사실을 제목이나 본문에 명시한다.

### C. 화면·상호작용 검증

1. 역할별 주요 route를 직접 연다. 목록에서 상세로 가는 흐름과 상세 URL 직접 진입을 모두 확인한다.
2. 좁은 화면의 잘림, 가로 스크롤, 한글 줄바꿈, 고정 버튼 도달 가능성을 확인한다.
3. 키보드 초점, Tab 순서, Escape 닫기, 창을 닫은 뒤 초점 복원을 확인한다.
4. 콘솔 오류, 중복 요청, 404·5xx 네트워크 요청을 화면 결과와 함께 묶는다.

### D. 전체 흐름·기존 발견 대조

1. §0에서 선언한 범위 안에서만 W군 핵심 사슬과 비동기 AS군을 실행한다. `재실행 안 함`이면 이 절의 시나리오 실행을 건너뛴다.
2. Notion `QA 요청` 목록을 먼저 대조해 이미 알려진 문제·회귀·실행 공백을 나눈다.
3. 현재 열린 GitHub Issue를 읽어 Notion에 없는 항목만 보조 대조한다.
4. Issue·Notion 행을 닫거나 수정하지 않는다. 쓰기 작업은 사용자가 명시한 경우에만 한다.

## 5. 증거 기록

각 발견 항목에 아래 정보만 남긴다.

- 후보 SHA와 실행 환경
- 역할, route 또는 API, 사전 상태
- 재현 단계
- 실제 결과와 기대 결과
- 영향과 심각도
- 로그·응답·스크린샷 참조
- 실행 재현, 자동 테스트, 코드 점검 중 어떤 근거인지

스크린샷은 식별 정보와 실데이터를 제거한 뒤 사용한다.
파일명은 `qa-id-role-route-viewport.png`처럼 재현 조건을 드러내고 개인 머신 경로는 문서에 쓰지 않는다.

## 6. Notion에 적을 때

사용자가 Notion 기록을 요청한 경우에만 작성한다.
토스의 라이팅 원칙 중 명확성, 간결성, 쉬운 말, 존중을 QA 문장에 적용한다.

### 6.1 중복 등록 금지 (작성 직전 필수)

새 행을 만들기 전에 `QA 요청` DB를 다시 조회하고, 아래 중 **하나라도** 기존 행과 맞으면 생성하지 않는다. 기존 행 URL만 보고한다.

- 제목 핵심 구문이 같거나 한쪽이 다른 쪽을 포함
- 같은 `Front URL`(path 기준) + 같은 `확인 역할` + 같은 증상 요지
- `문제 내용`의 핵심 문장(실패 현상·route·역할)이 실질 동일
- 본문에 적힌 기준 SHA·회차와 같은 관찰을 다시 적는 경우

전수 QA 결과를 한 번에 대량 재적재하지 않는다. 신규로 판정된 항목만, 요청 범위 안에서 1건씩 추가한다.

### 6.2 문장

- 제목은 `조건에서 관찰된 문제` 순서로 쓴다.
- 본문은 관찰 결과, 기대 동작, 검증 기준을 2~4문장으로 쓴다.
- 한 문장에는 한 메시지만 담는다.
- `stub`, `seam`, `provision` 같은 용어는 재현에 꼭 필요하지 않으면 쉬운 한국어로 바꾼다.
- 확인하지 않은 영향은 단정하지 않는다.
- 군더더기, 감탄, 압박, 해결책 추측은 뺀다.
- 기존 상태, 담당자, 체크값은 요청 없이 바꾸지 않는다.

작성 뒤 대상 수, 제목 중복, 빈 본문, 상태 변경, 스크린샷 첨부 수를 다시 조회해 검증한다.
Notion 본문이나 비공개 링크를 저장소 문서에 복사하지 않는다.

## 7. 출시 판정

아래 셋 중 하나로 끝낸다.

- `RELEASE READY`: 출시 핵심 흐름이 통과했고 알려진 잔여 위험이 출시를 막지 않는다.
- `RELEASE BLOCKED`: 사용자가 일을 끝낼 수 없거나, 데이터·권한·개인정보가 위험하거나, 핵심 실패가 조용히 숨는다.
- `QA INCOMPLETE`: 환경·권한·fixture 부족으로 핵심 경로를 검증하지 못했다.

최종 보고에는 exact SHA, 실행한 범위, 통과·실패·미실행 수, blocker, 기존 Issue와의 관계, 증거 위치를 적는다.
main이 이후 이동했다면 현재 SHA와의 차이를 한 줄로 알리고 결과가 고정 후보에만 유효하다고 명시한다.

## 완료 확인

- [ ] exact 후보 SHA를 기록했다.
- [ ] Notion `QA 요청`을 선조회했고 §0 범위를 선언했다.
- [ ] 선언 범위 밖의 전수 재실행·동일 증상 재등록을 하지 않았다.
- [ ] 기존 자동 검증과 (범위 안) 역할별 핵심 흐름을 확인했다.
- [ ] 모바일·키보드·한글 표시를 범위에 포함했을 때만 확인했다.
- [ ] Notion 기존 행과 열린 Issue에 발견 항목을 대조했다.
- [ ] source finding과 실행 재현을 구분했다.
- [ ] 증거에서 실데이터와 개인 경로를 제거했다.
- [ ] 제품 코드와 외부 상태를 무단으로 수정하지 않았다.
- [ ] 출시 판정과 main drift를 명확히 보고했다.
