# 가독성 규칙

PR 본문·코멘트·티켓 본문이 전부 이 파일을 가리킨다.
다른 파일에 가독성 불릿을 다시 쓰지 않고 이 파일로의 링크 한 줄로 대신한다 — 사본은 원본이 바뀔 때 조용히 갈라진다.

## 토스의 원칙을 협업 글에 적용한다

출처: [토스의 8가지 라이팅 원칙들](https://toss.tech/article/8-writing-principles-of-toss).
아래는 토스의 UX 원칙을 OSS Hub의 PR·댓글·Issue에 적용한 기준이지, 토스가 정한 PR 규칙은 아니다.
원문처럼 원칙은 방향이며 기계적인 합격 기준이 아니다 — 글자 수·줄 수·섹션 수를 맞추려 의미를 자르거나 의례를 추가하지 않는다.

1. **Predictable hint — 다음 행동과 결과를 알린다.** 무엇을 확인·결정하면 어떤 결과가 생기는지 쓴다. 제안의 기대 결과와 실제 검증 결과는 구분한다.
2. **Weed cutting — 의미 없는 단어를 뺀다.** 빼도 뜻이 같은 수식어를 지우되 기술 식별자와 조건은 남긴다.
3. **Remove empty sentences — 빈 문장을 뺀다.** 제목·위젯·표가 이미 말한 내용을 반복하거나 빈 공간을 설명으로 채우지 않는다.
4. **Focus on key message — 지금 필요한 결정을 앞세운다.** PR은 수용할 변화, 댓글은 판단과 다음 행동, Issue는 해결할 문제와 착수 조건부터 보여 준다. 상세 근거는 아래로 옮기되 없애지 않는다.
5. **Easy to speak — 말로도 이해되게 쓴다.** 쉬운 구어체로 한 문장에 한 메시지를 담고, 필요한 전문 용어는 정확한 이름과 짧은 설명을 함께 쓴다.
6. **Suggest over force — 선택과 필수 수정을 구분한다.** 비차단 제안에는 선택지를, 반드시 고칠 결함에는 근거·영향·승인 조건을 쓴다. 강요나 공포로 설득하지 않으며 필수 수정을 선택 사항으로 낮추지도 않는다.
7. **Universal words — 사람 대신 사실을 설명한다.** 은어·밈·인신평가 대신 누구나 확인할 구체적인 사실을 쓴다. 「AI slop」이라고 평가하지 말고 중복 구현이나 불필요한 추상화가 어디에 있는지 설명한다.
8. **Find hidden emotion — 읽는 사람의 부담을 줄인다.** 작성자의 수정 비용과 리뷰어의 확인 부담을 고려해 필요한 범위와 이유를 밝힌다. 빈 칭찬이나 공감 문구를 의무로 넣지 않는다.

## 근거와 형식

간결함을 이유로 기술 식별자·근거 링크·재현법·권한·오류 처리·원자성 경계·검증 한계·필수 증거·승인 조건을 삭제하지 않는다.
기존 파일 수정·재사용으로 줄일 수 있는지 먼저 보되, 파일 수를 줄이려고 필요한 안전 경계를 합치지 않는다.

1. **여는 말이 결론이다** — 템플릿의 티켓 연결·시작 블록은 유지하고, 첫 설명에서 「내가 다음에 무엇을 하나」를 알린다.
2. **첫 화면에 결론·다음 행동을 둔다** — 리뷰는 블로킹 여부와 승인 조건도 여기에 쓴다. 화면 주장이면 필요한 이미지를 함께 보인다.
3. **한 불릿 = 한 사실** — 서로 다른 판단이 섞이면 나눈다.
4. **문단은 짧게 쓴다** — 훑기 어려울 때 불릿이나 표로 바꾸되 고정 줄 수를 강제하지 않는다.
5. **여러 대안을 같은 기준으로 비교할 때 표를 쓴다** — 한 가지 제안·유지 의견은 짧은 문장으로 충분하다. PR의 필수 Before/After 표는 해당 증거 게이트를 따른다.
6. **화면은 이미지, 변경 흐름은 다이어그램으로 증명한다** — 형식을 채우려 도식을 만들지 않는다. 코드 인용은 판단에 필요한 부분만 fenced block으로 보인다. 구체적인 필수 증거는 각 스킬의 게이트를 따른다.
7. **숫자는 표나 한 줄에 둔다** — 문장 속에 수치를 나열하면 어느 것이 중요한 숫자인지 묻힌다.
8. **강조는 문단에 하나다** — 볼드가 셋이면 없는 것과 같다.
9. **같은 말을 두 번 하지 않는다** — 제목이 말한 것, 위젯이 말한 것, 표가 말한 것을 문장으로 되풀이하지 않는다.
10. **파일 근거는 클릭 가능한 링크로 쓴다** — `파일명:줄` 또는 「기존 snapshot 조회」처럼 증명 대상을 이름으로 쓴다. 긴 경로는 링크 대상에 맡기고, 리뷰 근거는 확인한 HEAD의 줄 링크를 보존한다.
11. **섹션 제목은 독자가 찾는 질문에 답한다** — 「유지할 동작」「판단 근거」처럼 쓰고 번호는 붙이지 않는다. 짧은 수용·유지 의견은 제목 없이 끝낸다. 답글의 지적 번호와 PR 템플릿의 필수 제목은 유지한다.
12. **긴 문장은 의미 단위로 나눈다** — 조건과 결과를 갈라 뜻이 바뀌지 않는지 확인한다.
13. **말투는 쓰는 사람의 말투다** — 에이전트 문체(「~하였습니다」)로 다듬지 않는다. 다듬는 순간 누가 판단했는지가 본문에서 사라진다.

## 자기 점검

올리기 전에 다섯 줄로 확인한다.

- [ ] 첫 설명에서 결론을 알 수 있고, 위 8원칙으로 불필요한 말과 독자의 부담을 점검했다.
- [ ] 첫 화면에 다음 행동이 있고, 리뷰라면 블로킹 여부·승인 조건도 보인다.
- [ ] 필요한 증거를 갖췄고, 형식을 채우기 위한 표·도식은 없다.
- [ ] 제목·위젯·표가 이미 말한 것을 문장으로 되풀이하지 않았다.
- [ ] 상세를 아래로 내린 뒤에도 의미·필수 근거·안전 경계·검증 한계가 남아 있다.
