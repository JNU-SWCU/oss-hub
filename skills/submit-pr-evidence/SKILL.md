# Submit PR Evidence

증거가 없으면 OSS Hub PR을 열지 않는다.
성공 기준은 PR이 계약과 정확히 일치하고, 해당되는 완료 조건이 열기 전에 실증되며, 경계 밖 파일을 건드리지 않는 것이다.

## Output contract

산출물은 `scripts/check-pr-body.sh`와 `scripts/check-public-safe.sh`를 통과한 PR 본문 파일이다.
첫 줄은 `Closes #<번호>`, `Refs #<번호>`, 또는 비어 있지 않은 `티켓 없음 — <이유>`다.
이슈 완료 조건을 이번 PR이 모두 채웠으면 `Closes`다.
증거 있는 PR 범위는 병합 가능하지만 이슈 의무가 남으면 `Refs`다.
있는 이슈를 `티켓 없음`으로 바꾸지 않는다.
해당되는 Before/After·흐름 다이어그램·확인 링크가 본문에 있고, 해당 없는 절만 아래 예외 문구로 시작한다.
해당되는 증거를 만들지 못했으면 PR을 열지 않고, Issue를 만들지 않으며, 못 찍은 화면을 면제로 바꾸지 않는다.

## 작업 표면

이 스킬은 PR 본문·증거 게이트만 소유한다.
해당 없는 표면은 다른 스킬로 넘기고 이 절차의 인터뷰·캡처·설치를 시작하지 않는다.

| 표면 | 이 스킬 | 계약 | 인터뷰 | 캡처 | 다이어그램 | 안티패턴 |
| --- | --- | --- | --- | --- | --- | --- |
| 티켓 없는 docs-only·설정 PR | 예 | 티켓 없음 한 줄 + 승인된 범위·완료·비범위 | 아니오 | 면제 사유 | 면제 사유 | 면제 사유 |
| 화면을 건드린 PR | 예 | Issue 또는 티켓 없음 | 미답 의도만 | 필수 | 로직이 바뀌면 | 필수 |
| 비시각 브라우저 라우팅·런타임 경계 (렌더 컴포넌트 불변) | 예 | Issue 또는 티켓 없음 | 아니오 | 필수(동작 표) | 로직이 바뀌면 | 면제 사유 |
| backend 로직 + 소비 화면 | 예 | Issue 또는 티켓 없음 | 화면 미답만 | 필수 | 필수 | 필수 |
| backend 로직, 화면 없음 | 예 | Issue 또는 티켓 없음 | 아니오 | 면제 사유 | 필수 | 면제 사유 |
| 릴리스 보고 전용 QA | 아니오 — `run-release-qa` | — | — | — | — | — |
| PR·Issue 코멘트만 | 아니오 — `write-github-comment` | — | — | — | — | — |

이미 받은 범위·완료 조건·하지 않을 것을 다시 묻지 않는다.
문서·설정 PR을 UI 질문으로 막지 않는다.

## 계약

번호가 있는 Issue면 `gh issue view <번호>`로 아래 세 섹션만 읽는다.
티켓 없는 작업이면 Issue를 조회하거나 만들지 않는다.
사용자가 승인한 범위·완료 조건·하지 않을 것과, 티켓이 없는 이유를 받은 뒤에만 진행한다.
로컬 작업을 공개하려고 Issue를 발명하지 않는다.
공유 경로 예약 Issue는 이 스킬이 만드는 QA/구현 티켓이 아니다.

섹션 이름은 2026-09-02 이후 발행 티켓 기준이며, 그 전 티켓은 괄호 이름을 쓴다.

- `할 일`(구 `최소 요구 (기능)`) — 구현할 최소 범위.
- `완료 조건`(구 `완료 조건 (기능 검증)`) — 열기 전 실제로 증명할 항목.
- `하지 않을 것 (이 티켓의 경계)`(구 `절대 금지 (이 티켓의 경계)`) — 건드리면 안 되는 파일·동작.

세 섹션 중 하나가 비어 있으면 구현을 시작하지 않는다.
빈 `하지 않을 것`은 경계 없음이 아니라 미기록이다.
`선행 의존성`이 미충족이거나 순환이면 부분 구현을 시작하지 않고 그 번호를 보고한다.

코드를 쓰기 전에 [루트 AGENTS.md](../../AGENTS.md)와 관련 중첩 AGENTS.md를 읽는다.
보안·PR 범위는 [docs/rules/security.md](../../docs/rules/security.md), [docs/rules/pr-scope.md](../../docs/rules/pr-scope.md)가 원본이다.
`할 일`만 구현하고 `하지 않을 것`에 적힌 경로는 0건 수정한다.
완료 조건은 한 항목씩 실제로 구동한 뒤에만 체크한다.

**초록불이 「돌았다」는 뜻은 아니다.** 워크스페이스 이름은 `backend`·`frontend`다.
없는 이름으로 필터하면 pnpm이 아무것도 실행하지 않고 exit 0을 낸다.
배열 플래그 뒤 경로는 ignore 값으로 먹힐 수 있다.
검증 보고에는 실행된 suite·test 개수를 적고, 개수가 없으면 통과를 주장하지 않는다.
이 수치는 PR 본문 `## 검증`에만 둔다 — 리뷰 답글로 옮기지 않는다([리뷰 답글 작성 원칙](../write-github-comment/SKILL.md#초록불이-말해-주는-것은-쓰지-않고-초록불이-감추는-것을-쓴다)).
lint와 typecheck가 통과해도 rebase 잔여물이 옛 코드를 먼저 반환할 수 있다. 전체 테스트만이 그것을 잡는다.

## 증거 게이트

완료 조건을 증명한 뒤, 변경에 **실제로 해당하는** 증거만 요구한다.
해당되는 증거가 없으면 제출을 막는다.
해당 없는 절은 비어 있지 않은 사유가 있는 예외 문구로만 면제한다.
찍지 못한 화면, 띄우지 못한 상태, 그리지 못한 흐름은 면제가 아니다.

적용 여부는 사람이 diff를 보고 판단한다.
`scripts/check-pr-body.sh`는 본문 형식만 검사하며 해당 여부를 대신하지 않는다.

### 화면·브라우저·소비 화면 → 캡처

변경이 사용자가 보는 화면, 브라우저 동작, 또는 backend가 바꾼 응답을 그리는 화면에 닿으면 Before/After가 해당된다.
backend만 고쳤어도 그 API를 소비하는 화면을 찍는다.
응답이 바뀌는데 화면이 같아 보이면 그 사실 자체가 리뷰 정보다.
브라우저 라우팅·런타임 경계만 바뀌고 렌더된 컴포넌트가 없어도 Before/After는 해당된다.
이 경우 `Before/After 없음`은 쓰지 않는다.
캡처를 못 만들었으면 본문에 N/A를 적지 말고 중단한다.
일반 스크린샷 면제는 없다.

공통 필수 — 실제 Before/After 이미지, After desktop과 390x844 전체 화면, `https://jnu-oss-hub.com/<path>` 확인 링크, 캡션의 source SHA·route·viewport·합성 상태, 공개 안전 사람 확인, 공개 첨부.
isolated origin이 다르면 그 차이를 적는다. 전체 URL이 같다거나 새 실행이라고 쓰지 않는다.

갈래·표·캡션·게시는 [references/frontend-capture.md](references/frontend-capture.md)가 원본이다.

- **시각·컴포넌트 변경** — `| 요소 |` 행이 필수다. 바뀐 컴포넌트마다 한 행이고 Before와 After는 같은 selector로 찍는다. 티켓에 `현재 화면` selector가 있으면 그대로 재사용한다.
- **비시각 브라우저 변경** — 렌더된 컴포넌트가 그대로인 라우팅·런타임 경계 변경. 요소 행을 지어내지 않는다. `## Before / After`를 `비시각 브라우저 변경 — <비어 있지 않은 이유>`로 열고 `| 동작 |` 표에 실제 브라우저·API 동작과 전체 화면 첨부를 넣는다. 이 선언은 면제가 아니다.

상태가 여럿이면 빈 상태·결과 없음·오류 중 해당하는 것을 추가로 찍는다.
로컬 경로를 적으면 첨부가 아니다.
요소 selector 절차는 시각 갈래만 manage-qa-tickets의 `qa-dom-capture`가 원본이다.
촬영 환경은 [references/evidence-harness.md](references/evidence-harness.md)가 원본이다.
수동 점검은 Aside CLI, 자동 회귀는 기존 Playwright 엔트리이며 서로 대신하지 않는다.
일상 확인은 실제 backend를 붙인 `pnpm dev`다. 미리보기 서버나 백엔드 없는 에뮬레이터를 만들지 않는다.

### backend 로직 → 흐름 다이어그램

분기·상태 전이·인가 경로·재시도 처리·호출 순서·계층 경계 중 하나라도 바뀌면 mermaid(우선) 또는 DOT로 `## 흐름 다이어그램`에 넣는다.
첫 그림은 입구 → 판단 → 결과, 노드 8개 이하다.
상세는 `<details>`에 둔다.
규칙은 [references/backend-diagram.md](references/backend-diagram.md)가 원본이다.
해당되면 대략적인 그림으로 대체하지 않고, 없으면 제출을 막는다.

### 해당 없는 절

스크립트·CI·문서·설정만 바꿔 사용자가 볼 화면이 없고 backend 흐름도 안 바뀌면 캡처·다이어그램·안티패턴을 적용하지 않는다.
브라우저 라우팅·런타임 경계 변경은 화면이 같아 보여도 여기 해당하지 않는다.
그때만 예외 문구에 비어 있지 않은 사유를 한 줄 남긴다.

## 화면 UX와 diff 검토

화면이 해당되면 [references/ux-antipatterns.md](references/ux-antipatterns.md) 스물세 항목을 통과시킨다.
판정 표는 `<details>` 안에 둔다.
발견한 위반은 열기 전에 고친다. 경계 밖일 때만 별도 티켓으로 남긴다.

모든 PR은 범위에 맞는 diff 검토를 한다.
과잉 구현을 걷어내되 검증·오류 처리·보안·접근성은 줄이지 않는다.
ponytail이 이미 있으면 `/ponytail-review`로 같은 점검을 해도 된다.
없으면 설치하지 않는다.
지적과 저장소 규칙이 부딪히면 저장소 규칙이 이긴다.
ponytail 결과를 근거 없이 「통과」로 적지 않는다.

## 인터뷰

화면이 해당되고, 아래 답이 아직 없을 때만 작성자에게 묻는다.
에이전트가 대신 답하지 않는다.
이미 받은 답을 재질문하거나 문서 PR을 화면 질문으로 막지 않는다.

1. **의도** — 「이 화면을 쓰는 사람이 여기서 제일 하고 싶은 일이 뭔가요? 한 문장으로 말해 주세요.」
   티켓 문구를 그대로 옮긴 답은 다시 묻는다.
2. **위화감** — 「방금 직접 눌러보셨잖아요. 어색했던 지점이 있나요? 없다면 어디서 어디까지 눌러보고 그렇게 판단하셨나요?」
   눌러본 경로를 말하지 못하는 「없음」은 확인하지 않았다는 뜻이다.
3. **안티패턴** — 「[스물세 항목](references/ux-antipatterns.md) 중 이 화면에서 특히 지켜야 하는 건 무엇이고 왜 그렇게 보세요?」

답은 1번 `## 무엇이 좋아지나`, 2번 `## 이 흐름이 자연스러운가`, 3번 `## UX 안티패턴 점검` 마지막 줄로 옮긴다.
말버릇을 다듬지 않는다.
2번에서 어색함이 나오면 열기 전에 고치고 `## 내가 고친 UX 문제`에 적는다.

답이 Issue 방향을 뒤집으면 고친 뒤 티켓 본문 `할 일`도 새 방향으로 다시 쓰고, 옛 방향 코드·상수·테스트도 걷어낸다.
티켓 없는 작업이면 Issue를 만들지 않고, 사용자와 범위·완료·비범위를 다시 합의한 뒤에만 진행한다.

## 로컬 관문

- **`docs/handoff/team-state/<GitHub 아이디>.md`에 이번 작업 항목이 있어야 한다.** pre-push 훅이 검사한다. 본문은 리뷰어에게 무엇이 좋아지는지를, 저널은 다음에 이 코드를 만질 사람에게 무엇을 조심할지를 말한다.
- **`corepack pnpm exec prettier --check .`가 통과해야 한다.** 훅이 저장소 전체를 본다.

## PR 본문 순서

템플릿은 [`.github/pull_request_template.md`](../../.github/pull_request_template.md) 하나다.
[`scripts/check-pr-body.sh`](../../scripts/check-pr-body.sh)가 절 제목과 예외 문구를 글자 단위로 검사한다.

사람이 읽는 것을 위에, diff가 이미 말하는 것을 아래에 둔다.

- `Closes #<번호>` · `Refs #<번호>` · `티켓 없음 — <이유>` — 계약을 바로 연다. 이슈 완료 조건을 채웠으면 Closes, 증거 있는 PR 범위는 병합 가능하지만 이슈 의무가 남으면 Refs, 티켓이 없을 때만 티켓 없음.
- `## 무엇이 좋아지나` — 누가 무엇을 할 수 있게 됐는지.
- `## 바로 확인` — 눌러볼 경로.
- `## Before / After` — 화면은 표와 이미지로 증명한다.
- `## 이 흐름이 자연스러운가` / `## 내가 고친 UX 문제`
- `## UX 안티패턴 점검`
- `## 흐름 다이어그램` / `## 검증`
- `## 정리` — 본문 맨 마지막. `- 디자인 규격:` 줄에 이번 PR이 쓴 공용 컴포넌트·토큰과 그 규격 출처(docs/design.md 컴포넌트 카드 이름 또는 Figma 컴포넌트 링크)를 적는다. 새 색·새 컨트롤을 직접 만들었으면 그 사실과 이유를 적는다.

예외 문구는 해당 없을 때만 쓰며, 이 문자열로 시작하는 한 줄이고 사유가 비어 있으면 안 된다.
못 만든 해당 증거에 이 문구를 쓰지 않는다.
`비시각 브라우저 변경 — <이유>`는 예외 문구가 아니다. Before/After 절 안에 그 선언과 `| 동작 |` 표를 남긴다.

- 바로 확인: `확인 링크 없음 — <산출물 위치 또는 이유>`
- Before / After: `Before/After 없음 — <이유>`
- 이 흐름이 자연스러운가: `화면 없음 — <이유>`
- 내가 고친 UX 문제: `화면 없음 — <이유>`
- UX 안티패턴 점검: `UX 안티패턴 해당 없음 — <이유>`
- 흐름 다이어그램: `흐름 다이어그램 없음 — <이유>`
- 정리의 디자인 규격: `화면 변경 없음 — <이유>`

`내가 고친 UX 문제`가 비어 있으면 직접 눌러보지 않은 것이다.
0건이면 무엇을 검토했고 왜 문제가 없었는지를 문장으로 적는다.

본문은 저장소 밖 파일로 먼저 쓰고 `bash scripts/check-pr-body.sh <본문 파일>`을 통과시킨다.
Claude Code hook은 통과하지 않은 본문의 `gh pr create`를 막는다.
다른 runtime에는 그 hook이 없으므로 이 단계와 템플릿 체크박스가 방어선이다.

## PR 본문 작성 원칙

### 여는 문단은 페르소나 언어로 쓴다

- `## 무엇이 좋아지나`는 "무엇을 고쳤다"가 아니라 "누가 무엇을 할 수 있게 됐다"로 쓴다.
  - 나쁨: `마일스톤 수정을 독립 Radix Dialog로 분리했습니다.`
  - 좋음: `교직원이 프로그램 편집에서 마일스톤을 고칠 때, 페이지 스크롤과 분리된 레이어에서 편집하고 저장 후 원래 자리로 돌아옵니다.`
- 컴포넌트·라이브러리 이름은 상세 절에 둔다.

### 검증은 사람이 확인한 행동으로 적는다

- 수치만으로 무엇을 보장하는지 알 수 없다.
- 수치 옆에 그 수치가 보장하는 사용자 행동을 적는다.

### 로컬 환경 잡음을 본문에 넣지 않는다

- `node_modules` 누락, Windows EPERM, 무관한 기존 경고는 필요하면 write-github-comment로 남긴다.
- 실행하지 못한 검증은 본문에 남긴다.

### 가독성

원본은 [references/readability.md](references/readability.md)다.
올리기 전에 그 파일 끝 자기 점검을 통과시킨다.

### 미첨부 placeholder를 남긴 채 열지 않는다

- `<!-- 첨부 대기: … -->`는 증거 게이트 미통과다.
- 해당 캡처를 못 만들었으면 주석이 아니라 제출을 멈춘다.

### 열기 전에 렌더된 본문을 다시 읽는다

- `\title`은 탭 + `itle`로 그려진다.
- 백슬래시·백틱·표·이미지가 의도대로인지 연 뒤 다시 확인한다.

## PR을 연다

1. `bash scripts/check-public-safe.sh`로 변경 파일·커밋 메시지의 public-safe 위반을 검사한다. PUBLIC repo이므로 본문·코멘트에도 같은 기준을 적용한다. 텍스트만이면 [references/public-safety-check.md](references/public-safety-check.md)의 `--text-only`를 쓴다.
2. `gh pr create --body-file <경로>`로 연다. 브랜치명·커밋 형식은 [AGENTS.md](../../AGENTS.md)가 원본이다. 연 뒤 `gh pr view <n> --json body`로 본문을 다시 읽는다.
3. 연리면 [프로젝트 보드](https://github.com/orgs/JNU-SWCU/projects/1)에서 해당 카드를 In Review로 옮긴다. 티켓 없는 PR이면 없는 카드를 만들지 않는다.
4. Notion에서 발행된 티켓이면(Issue 본문에 `QA<번호>` 참조) PR URL을 Issue에 코멘트로 남긴다. Notion 행은 손대지 않는다.

## 리뷰 답글 작성 원칙

리뷰 지적 답글, UX 제안, Issue 진행 코멘트는 write-github-comment가 원본이다.
이 문서에 남는 PR 본문 규칙은 하나다: **`## 검증`은 열 때 끝나는 절이 아니다.** 다시 돌렸으면 그 절을 갱신한다.

## 멈추는 때

- 선행 의존성 미충족 또는 순환 → 번호를 보고 멈춘다. 의존성 수정은 발행자 몫이다.
- 해당 증거를 만들 수 없음 → 추측 이미지·목업·대략 다이어그램·면제 문구로 대신하지 않고 멈춘다.
- 계약이 구현에 필요한 지점에서 침묵 → 과거 티켓 기억으로 추론하지 않고 사용자에게 묻는다.
- 세 실행 계약이 비어 있음 → 채울 때까지 구현하지 않는다.
- 티켓 없는 작업에 범위·완료·비범위 또는 이유가 없음 → Issue를 만들지 않고 사용자에게 받는다.

## 하지 않는 것

- 로컬 파일 경로를 본문에 적고 첨부했다고 하지 않는다.
- 증거 이미지를 제품 브랜치에 커밋하지 않는다([pr-scope.md](../../docs/rules/pr-scope.md) §1).
- 증거 전용 브랜치를 만들지 않는다.
- `gh release create`로 증거용 Release를 새로 발행하지 않는다. 이미 발행된 Release에 파일을 더하는 절차는 [frontend-capture.md](references/frontend-capture.md#이미-발행된-release-에-에셋으로-올린다)를 따른다.
- `/artifacts/`에 두지 않는다.
- 목업·Figma·테스트 출력·코드 diff로 실행 화면이나 실제 흐름을 대신하지 않는다.
- 백엔드 없는 검토 서버, 호환 플래그, 에뮬레이터 카탈로그를 만들지 않는다.
- 해당 캡처 실패를 `Before/After 없음`으로 바꾸지 않는다.
- 렌더되지 않은 컴포넌트의 `| 요소 |` 행을 지어내지 않는다.
- 비시각 브라우저 변경에 `Before/After 없음`이나 N/A를 쓰지 않는다.
- isolated origin 차이를 숨기거나 전체 URL이 같다·새 실행이라고 쓰지 않는다.

## 요구사항

- `gh` — Issue가 있을 때의 view, PR 생성, 보드 카드 이동.
- `git` — [AGENTS.md](../../AGENTS.md) 브랜치·커밋 흐름.
- `bash scripts/check-public-safe.sh`
- `bash scripts/check-pr-body.sh <본문 파일>`
- 화면 수동 점검이 해당되면 설치된 Aside CLI(`aside`, `aside repl`). 없는 명령을 만들지 않는다.
- 브라우저 자동 회귀가 해당되면 기존 `pnpm --filter frontend e2e`.

## 완료 체크리스트

- [ ] Issue면 세 계약 섹션을 읽었고, 완료 조건을 모두 채웠으면 `Closes #<번호>`, 증거 있는 PR 범위는 병합 가능하지만 이슈 의무가 남으면 `Refs #<번호>`다. 티켓 없으면 승인된 범위·완료·비범위와 `티켓 없음 — <이유>`가 있다. 있는 이슈를 티켓 없음으로 쓰지 않았다. 선행 의존성 미충족·순환이면 착수하지 않았다.
- [ ] 첫 수정 전에 루트와 관련 중첩 AGENTS.md를 읽었다.
- [ ] 금지 경로를 0건 수정했다.
- [ ] 완료 조건 각 항목을 실제 증거로 실증했다.
- [ ] 화면·브라우저가 해당되면 Before/After가 있다. 시각 변경은 `| 요소 |` 같은 selector 행이고, 비시각 브라우저 변경은 `비시각 브라우저 변경 — <이유>`와 `| 동작 |` 표다. 실제 Before/After 이미지와 After desktop·390x844가 공개 첨부되며 SHA·route·viewport·합성 상태와 isolated origin 차이를 적었다. 공개 안전·메타데이터를 사람이 확인했다. 해당 캡처를 못 찍어 면제하거나 N/A로 바꾸지 않았다.
