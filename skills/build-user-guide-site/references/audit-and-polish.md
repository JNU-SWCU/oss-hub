# 시각 검수, 윤문, Aside 독자 시험

## 시각 검수 (`visual-audit`)

배포된 사이트를 대상으로 합니다. 언어 진입·수동 선택·기존 URL 호환성의 브라우저 검수 항목은 [localization.md](localization.md#검수)를 따릅니다.

```bash
node skills/build-user-guide-site/scripts/visual-audit.mjs [origin] [outJson]
```

- 기본 origin은 `https://jnu-swcu.github.io`이고 `<origin>/oss-hub/sitemap-0.xml`의 모든 페이지를 돕니다.
- 네 조합으로 열어 봅니다: 1440x900 라이트, 390x844 라이트, 1440x900 다크, 390x844 다크.
- 잡는 것: 콘솔 오류, 페이지 오류, HTTP 400 이상, 가로 스크롤, 깨진 이미지, 빈 alt, 넘치는 표/코드/이미지, 제목 단계 건너뜀, 깨진 내부 링크와 앵커.
- 출력 JSON은 기본으로 임시 폴더에 쓰고 경로를 출력합니다(저장소를 더럽히지 않습니다).
- 스크립트가 못 잡는 것은 사람이 봅니다. 다크 모드에서 흐린 이미지 테두리, 모바일에서 사이드바 동작, 이미지 클릭 확대.

이미지 파일을 검수해도 페이지에서 다시 잘릴 수 있으니 랜딩과 본문을 렌더링한 화면으로도 봅니다. 미리보기는 쓰지 않는 포트를 `127.0.0.1`에 명시해 띄우고, 화면이 예상과 다르면 포트를 먼저 확인합니다. 다시 찍은 이미지는 alt, caption, 본문 번호를 함께 대조합니다. 박스 위치나 컨트롤 종류(체크 칸과 스위치)가 바뀌어 있을 수 있습니다.

결과는 `Area / Observed / Expected / Evidence`로 보고하게 하고, 고치는 일은 오케스트레이터가 집필 담당에게 돌려줍니다.

품질을 말할 때는 잴 수 있는 수치만 씁니다. "최고 수준" 같은 말은 근거가 없으니 쓰지 않습니다. 빌드 결과(`dist/`)에서 깨진 내부 링크 수와 alt 없는 이미지 수를 세고, 대표 페이지 몇 개에 Lighthouse를 돌립니다.

```bash
npx -y lighthouse@12.6.0 <URL> --chrome-flags="--headless=new" \
  --only-categories=performance,accessibility,best-practices,seo --output=json --output-path=<scratch>/lh.json
```

성능 점수는 CDN이 식은 첫 요청에서 낮게 나옵니다. 낮으면 한 번 더 돌려 확인합니다. 사이트 제목 로고처럼 장식 이미지의 빈 alt는 정상입니다.

## 윤문 (`polish-<role>`)

언어별 기준은 [localization.md](localization.md)를 따릅니다. 한국어는 사실 확인 뒤 `humanize-korean` 스킬로 다듬고, 영어는 영어 독자 기준으로 교정합니다. 사실을 먼저 확정해야 윤문이 사실을 바꾸지 않습니다.

두 번 나눠 돌립니다. 1차는 조사, 번역투, 피동 같은 오류를 잡고, 2차는 역할별 에이전트가 끊기는 단문, 같은 어미 반복, 어긋난 주술 호응 같은 문장 흐름을 봅니다. 한 번에 맡기면 오류만 고치고 끝나기 쉽습니다. 오케스트레이터는 diff를 직접 읽고, 에이전트가 올린 사실 의심은 코드와 대조해 판단합니다.

MDX 안전 규칙(윤문 에이전트에게 알립니다):

- frontmatter, `import` 줄, 컴포넌트 태그(`<Steps>`, `<Shot>`, `<Success>`, `<Recover>`, `<Verified>`)와 그 속성(`src`, `alt`, `caption`, `status`)은 바꾸지 않습니다. `alt`와 `caption` 문장은 다듬어도 되지만 사람 이름과 아이디를 넣지 않습니다.
- 백틱으로 감싼 화면 라벨은 바꾸지 않습니다. 라벨이 틀렸다고 보이면 고치지 말고 보고합니다.
- 번호 목록의 번호와 이미지의 빨간 박스 번호의 대응을 깨지 않습니다.
- 링크 주소와 앵커, 표의 열 수, 코드 블록은 그대로 둡니다.
- 의미를 바꾸지 않습니다. 조건, 순서, 경고, 숫자를 지우거나 새 주장을 넣지 않습니다.
- 위험 경고는 해당 동작 직전에 남깁니다.

윤문 뒤에는 `cd guide && pnpm exec astro build --outDir <scratch>`로 빌드를 확인하고, `git diff`로 컴포넌트 속성과 라벨이 안 바뀌었는지 훑습니다. 번역투와 AI 투 기준은 `writer-brief.md`의 한국어 절입니다.

## 교정 (`proofread-<묶음>`)

윤문을 마친 가이드를 다시 읽을 때는 읽기 전용 에이전트 세 개를 병렬로 돌립니다. 묶음은 관리자와 서비스 소개·시작하기·FAQ, 학생, 교직원입니다. 각 에이전트는 이렇게 보고합니다.

- 파일마다 `wc -l` 줄 수와 읽은 줄 합계. 다 읽었다는 증거입니다.
- 제안은 많아야 15개, `파일:줄 — 원문 → 제안` 한 줄씩.
- 백틱 라벨과 사실은 건드리지 않습니다.

오케스트레이터는 제안을 고릅니다.

- 받습니다: 끊기는 단문 잇기, "해당" 바꾸기, 본문에서 빗금으로 이은 화면 문구 풀기.
- 버립니다: 새 사실이 들어가는 제안, 쌍점이나 어미를 맞추는 형식 통일, 화면 라벨인 빗금.

고를 때는 원문 문자열이 파일에 정확히 한 번 있는지 확인하고 바꾸는 작은 스크립트를 씁니다. 못 찾은 항목은 건너뛰지 말고 목록으로 출력합니다. 같은 문장이 두 군데 있으면 엉뚱한 곳이 바뀌기 때문입니다. 고친 개수는 `git diff --numstat`으로 셉니다. 역할별 개수를 짐작해 쓰면 틀립니다.

## 기존 이미지에 번호 박스 더하기

박스가 빠진 이미지 하나만 고칠 때는 다시 찍지 않고 Pillow로 덧그려도 됩니다. 원본을 임시 폴더에 먼저 복사하고, `capture-lib.mjs`와 같은 모양으로 그립니다. 둥근 빨간 박스(2배 이미지에서 두께 5px), 오른쪽 위에 흰 숫자가 든 빨간 원입니다. 그 뒤 본문 단계, alt, caption이 같은 번호를 가리키는지 맞춥니다. 화면이 바뀌었으면 덧그리지 말고 다시 찍습니다.

## Aside

Aside는 로그인된 실제 브라우저입니다. 그래서 두 가지에만 씁니다.

1. 독자 시험: 완성된 가이드를 처음 보는 사람처럼 따라 하며 격리 스택에서 막히는 곳을 찾습니다. 순서가 맞는지, 라벨이 화면과 같은지, 성공 신호가 보이는지를 봅니다.
2. 배포 주소 확인: `https://jnu-swcu.github.io/oss-hub/`가 열리고 새 변경이 반영됐는지 봅니다.

하지 않는 것:

- 캡처에 쓰지 않습니다. 실제 계정이 로그인된 브라우저라 실제 데이터가 화면에 찍힐 수 있습니다.
- 운영 서비스 화면을 열지 않습니다.

사용 전에 `aside guide`를 실행하고, CLI가 낡았거나 모르는 명령이면 `aside --update`를 먼저 합니다. 합성 세션 쿠키를 주입할 수 없으면 같은 읽기 순서를 Playwright 페르소나로 재현합니다(`capture-lib.mjs`의 `openAs`와 `visit`).

독자 시험의 결과는 "몇 번째 단계에서 무엇이 헷갈렸는가"로 적어 집필 담당에게 돌려줍니다.
