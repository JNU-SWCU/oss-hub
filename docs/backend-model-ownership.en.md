## Interpretation criteria

- Ownership does not mean one repository per table.
  The current ADR-003 §10 defines repositories by business-specific writes and screen-specific read questions.
- The direct references below were collected by scanning production src for delegate calls and SQL table literals, excluding fixtures/specs/support.
- This search alone does not fully establish nested relation writes in parent create/update calls, dynamic delegates, or external services/operations SQL.
  Failure to find a writer does not mean that a table is dead.
- Files in the Tx column are candidate boundaries containing a transaction client/$transaction.
  During each refactor, verify whether the calls share the same transaction through their execution paths and integration tests.
- Retention/deletion describes current code semantics; it does not establish new statutory retention periods or operational cleanup schedules.
- Public means only projections that pass controller/service eligibility and DTO allowlists, not entire rows.

## Canonical submission aggregate storage and compatibility APIs

`MilestoneDocumentSubmission`, `MilestoneDocumentSubmissionHistory`, and `MilestoneDocumentReviewHistory` are the current canonical stores for submissions, revisions, and reviews.
`submissions/repository/submissions.repository.ts` is the write adapter for the existing API that uses `LEGACY_MILESTONE_SUBMISSION` items, while `milestone-documents/repository/milestone-document-submission.repository.ts` owns submissions for individual DOCUMENT items.
The two APIs differ in public IDs, content shapes, and deadline/resubmission eligibility, so do not combine them into one policy branch.

Both paths perform membership locking, current-revision CAS, history appends, and file attachment inside the transaction started by their respective service.
Review detail/event writes use the narrow shared writer in `prisma/submission-review-writer.ts`, preserving review→event order on the compatibility path and event→review order on the DOCUMENT path.
Share only identical storage invariants, and preserve repeated decisions, historical nullable revisions, and the distinction between the history being reviewed and the review event.

`SubmissionRevisionContent` in review responses is the existing JSON contract, including scalar/null/array/object.
Do not force historical submissions into the current new-write content union through type assertions or reject reads by revalidating them against it.
New relationships or historical event backfills follow the separate schema decisions below.

## Decisions to separate from refactoring

1. **GithubRepository writers span multiple responsibilities.**
   Inventory observations, provisioning, OWN connections, explicit publication, and disconnection on program/team deletion each exist separately.
   Do not consolidate them based on the “single writer file” wording in data-modeling.md.
2. **Do not automatically apply a writer 0=dead rule.**
   Check raw SQL/nested mutations/operational jobs/readers of historical data first; production counts, checks for external usage, and backup/restore plans belong in a separate contract before a drop.
3. **Do not force-fill null provenance.**
   SubmissionHistory.revision, ReviewHistory.submissionHistoryId·resubmissionDueAt, and ProvisionJob.currentEventId may mean that historical facts are unknown or not applicable.
   Do not impose NOT NULL/backfill for TypeScript convenience.
4. **Separate relationship restructuring candidates from naming.**
   Person × year activity and repository × person × date contributions have different grains.
   Detached IDs in RepositoryIssuanceHistory and association evidence for outsider aggregates are also intentional.
   Standardizing them all as ordinary FKs changes deletion/retention semantics and therefore requires separate policy/migration work.
5. **Handle Collection*Fact renaming in a separate migration PR after confirming that row grain/readers remain unchanged.**
   Do not mix a mandatory History suffix into the current refactor.
6. **Program lifecycle removal belongs to #1466.**
   Actual production rows, consumers, and migration paths must be checked separately from code-boundary changes.
7. **Team-deletion notification write boundary:** the service builds notification payloads and recipient rules, then calls `TeamDeletionNotificationStore.createTeamDeletedNotifications`.
   The repository performs `skipDuplicates` writes in the same transaction, preserving notification → team tree deletion → audit order and full rollback on failure.
   Do not expose the Prisma notification delegate to the service.
8. **Do not combine the 2 new preparation models into the existing Team.**
   Participation during pre-submission preparation and a confirmed TeamMember’s unique program membership are different states.
   Using the existing 43-model checklist unchanged as the completion criterion would omit these two boundaries.

## Physical schema candidates and decisions to retain the current design

This code refactor does not adopt the candidates below.
The reference repository contains 77 migration files, two more than the original issue’s 75.
Do not treat file presence as a ledger of production application, and do not modify existing migrations.

Each proposed change follows this execution sequence.

1. Collect only counts and violation types during an approved read-only production audit.
   Do not copy actual personal-information rows into documents/fixtures.
   The operations owner checks external SQL/batches, retention policies, and the migration ledger.
2. Expand with new nullable columns/relationships and required indexes, and review concurrent old/new versions, lock duration, and additional write cost.
   The DB owner approves the migration and stop conditions.
3. Backfill only rows with proven provenance using rerunnable batches.
   Preserve ambiguous historical relationships and nulls; do not cut over failed batches.
4. Transition readers/writers while preserving transaction isolation, lock order, CAS, idempotency, and audit/outbox.
   Do not move external GitHub/storage calls inside transactions.
   Compare results, public IDs, repeated decisions, deletion/retention, and authorization races in an isolated DB.
5. Propose a separate contract migration only after equivalence and external consumer migration are confirmed.
   Specify a backup restoration test, application/DB rollback plans, cutover stop conditions, and who approves execution.
   If evidence is insufficient, return to the existing readers/writers and do not remove columns/data.
