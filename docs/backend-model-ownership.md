# 백엔드 모델의 소유·관계·쓰기/읽기 경계

기준: `main@8a6a141e7ad56b1efdb9e0ec5877bc6d27e9b80a`, 2026-10-20 KST.
기존 43개와 후속 추가 ApplicationPreparation·ApplicationPreparationParticipant 2개를 모두 포함한다.
이 문서는 정적 소스 조사다. 운영 행 수·외부 reader·수동 SQL job은 확인하지 않았다.
스키마/데이터/정책은 수정하지 않는다.

## 해석 기준

- 소유는 테이블마다 repository 하나라는 뜻이 아니다. 최신 ADR-003 §10의 업무별 쓰기와 화면 질문별 읽기 repository가 기준이다.
- 아래 직접 참조는 production src에서 delegate 호출과 SQL table literal을 스캔하고 fixture/spec/support를 제외한 목록이다.
- 부모 create/update의 nested relation 쓰기, 동적 delegate, 외부 서비스/운영 SQL은 이 검색만으로 완전 증명되지 않는다. writer 미검출은 죽은 테이블이라는 결론이 아니다.
- Tx 열의 파일은 transaction client/$transaction을 포함하는 경계 후보다. 각 호출이 동일 transaction에 들어가는지 개별 리팩터 때 경로와 integration test로 확인한다.
- 보존/삭제는 현재 코드상 의미이며 법정 보존기간·운영 정리주기를 새로 결정하지 않는다.
- public은 row 전체 공개가 아니라 controller/service eligibility와 DTO allowlist를 통과한 projection만 뜻한다.

## 제출 aggregate의 canonical 저장과 호환 API

`MilestoneDocumentSubmission`, `MilestoneDocumentSubmissionHistory`, `MilestoneDocumentReviewHistory`가 현재 제출·revision·검토의 저장 정본이다. `submissions/repository/submissions.repository.ts`는 `LEGACY_MILESTONE_SUBMISSION` 항목을 사용하는 기존 API의 쓰기 adapter이고, `milestone-documents/repository/milestone-document-submission.repository.ts`는 개별 DOCUMENT 항목 제출을 소유한다. 두 API의 공개 ID, content 형태, 마감·재제출 허용 조건은 동일하지 않으므로 하나의 정책 분기로 합치지 않는다.

두 경로는 각 service가 시작한 transaction 안에서 membership lock, 현재 revision CAS, 이력 추가와 파일 연결을 수행한다. 검토 detail/event 쓰기는 `prisma/submission-review-writer.ts`의 좁은 공통 writer를 사용하며, 호환 경로의 review→event 순서와 DOCUMENT 경로의 event→review 순서를 각각 유지한다. 공유는 같은 저장 불변식에 한정하고, 반복 판정·과거 nullable revision·검토 대상 이력과 검토 사건의 차이를 보존한다.

검토 응답의 `SubmissionRevisionContent`는 scalar/null/array/object를 포함하는 기존 JSON 계약이다. 과거 제출을 현재 신규 쓰기 content union으로 강제 단언하거나 재검증해서 읽기를 거부하지 않는다. 새로운 관계나 과거 사건 backfill은 아래 별도 스키마 판단을 따른다.

## 리팩터와 분리할 판단

1. **GithubRepository writer는 여러 책임으로 나뉜다.** inventory 관측, provisioning, OWN 연결, 명시 공개, 프로그램/팀 삭제의 연결 해제가 각각 존재한다. data-modeling.md의 “유일 writer 한 파일” 문구를 근거로 합치지 않는다.
2. **writer 0=dead 규칙을 자동 적용하지 않는다.** raw SQL/nested mutation/운영 job/옛 데이터 reader를 먼저 확인하고, drop은 운영 count·외부 사용 확인·백업/복원 계획을 별도 계약으로 둔다.
3. **null provenance를 강제로 채우지 않는다.** SubmissionHistory.revision, ReviewHistory.submissionHistoryId·resubmissionDueAt, ProvisionJob.currentEventId는 과거 사실을 모른다는 상태이거나 비해당을 뜻한다. TypeScript 편의를 위해 NOT NULL/backfill하지 않는다.
4. **관계 재편 후보는 이름과 분리한다.** 사람×연도 활동과 저장소×사람×날짜 기여는 grain이 다르다. RepositoryIssuanceHistory의 detached ID와 outsider aggregate의 연결 증명도 의도다. 일반 FK 통일은 삭제/보존 의미를 바꾸므로 별도 정책·migration 작업이다.
5. **Collection*Fact 개명은 행 단위/reader가 불변임을 확인한 뒤 별도 migration PR로 다룬다.** History 강제 접미사를 현재 리팩터에 섞지 않는다.
6. **Program lifecycle 제거는 #1466이다.** 코드 경계 변경과 별도로 실제 운영 행·consumer·migration 경로를 확인해야 한다.
7. **팀 삭제 알림 경계 후보:** `programs/service/program-teams.service.ts:69`의 `store.notificationWriter.notification.createMany`는 service가 transaction writer를 직접 쓰는 현재 예외다. 일반 서비스의 Prisma 소유 개선은 이 callback의 원자성·알림 payload·idempotency를 보존한 작은 별도 변경으로 판단한다.
8. **신규 준비 모델 2개를 기존 Team으로 합치지 않는다.** 제출 전 준비 참여 상태와 확정 TeamMember의 프로그램 내 유일 소속은 서로 다른 상태다. 기존 43개 체크리스트를 그대로 완료 기준으로 쓰면 이 두 경계를 누락한다.

## 물리 스키마 후보와 현행 유지 판단

이 코드 리팩터는 아래 후보를 채택하지 않는다. 기준 저장소의 migration 파일은 77개이며 최초 이슈의 75개에서 두 개가 추가되었다. 파일 존재를 운영 적용 ledger로 간주하지 않으며, 기존 migration은 변경하지 않는다.

| 후보 | 현재 유지안 | 변경안과 이익 | 변경 전에 필요한 근거·결정 |
| --- | --- | --- | --- |
| TeamMember 프로필 사본 | `name/department/email`을 읽지 않는 소속 writer와 UserProfile 정본 유지 | 세 열만 제거해 잘못된 fixture·정본 오해를 줄임 | 세 열의 non-null 건수·출처·외부 reader·보존/이전 승인. `programId`와 복합 FK/프로그램별 unique는 유지 |

각 변경안의 실행 순서는 다음과 같다.

1. 승인된 읽기 전용 운영 감사에서 건수와 위반 유형만 수집한다. 실제 개인정보 행을 문서·fixture에 복사하지 않는다. 운영 담당자는 외부 SQL/배치와 보존 정책, migration ledger를 확인한다.
2. 새 nullable 열/관계·필요 인덱스를 expand하고 구버전과 신버전의 동시 실행, lock 시간, 추가 쓰기 비용을 검토한다. DB 담당자가 migration과 중단 조건을 승인한다.
3. 출처가 입증되는 행만 재실행 가능한 batch로 backfill한다. 모호한 과거 관계와 null은 유지하고, 실패 batch는 전환하지 않는다.
4. 기존 transaction isolation·lock 순서·CAS·idempotency·audit/outbox를 유지한 채 reader/writer를 전환한다. 외부 GitHub/storage 호출을 transaction 안으로 옮기지 않는다. 결과·공개 ID·반복 판정·삭제/보존·권한 경쟁을 격리 DB에서 비교한다.
5. 동등성·외부 consumer 이전이 확인된 뒤 별도 contract migration을 제안한다. 백업 복원 시험과 애플리케이션/DB rollback 계획, cutover 중단점, 실행 승인자를 명시한다. 증거가 부족하면 기존 reader/writer로 돌아가고 열/데이터를 제거하지 않는다.

## 검증·제한

- schema model 선언 45개, 표 45개, 각 모델 PK/unique/FK/direct source index 생성 확인.
- SQL scan의 FROM/JOIN은 reader, INTO/UPDATE는 writer 후보로 구분했다. DELETE 내부 FROM 등의 문법적 중복은 원문 확인용이며 실행 횟수 집계로 사용하지 않는다.
- 이 증거만으로 외부 reader 부재, 운영 테이블 비어 있음, 법정 보존기간, 스키마 변경 승인까지 주장하지 않는다.
