# Todo 4 제출 축의 릴리스 경계

2026-11-04 확인한 운영 backend 이미지는 `oss-hub-backend:v0.24.32`다.
실제 컨테이너의 `dist/src/programs/milestone-documents.controller.js`에는
항목 제출·심사 경로가 있지만, `milestone-documents.repository.js`의
`findByMilestoneId`와 `findDocumentContext`는 `kind=DOCUMENT`로 제한한다.
운영 집계의 레거시 항목 6개와 그 제출 20개는 이 API로 전환할 수 없는 상태다.

따라서 프론트가 먼저 배포될 수 있는 두 앱의 배포 환경에서는 백엔드 준비
릴리스를 먼저 배포해야 한다. 새 화면을 현재 운영 백엔드와 조합해도
호환된다고 주장하지 않는다.

이 브랜치는 아래 1단계인 백엔드 준비를 담는다. 프론트 전환, 코드 참조
중단, 물리 삭제의 구현은 아직 포함하지 않았다. 이 단계들을 완성된 draft나
Todo 4 전체 완료로 표시하지 않는다. 가이드에는 준비 백엔드의 정책과 기존
화면에 남아 있는 입력 제약을 함께 안내한다.

## 배포 순서

1. **백엔드 준비:** 기존 마일스톤 제출 API, `kind`,
   `Milestone.submissionType`과 물리 `legacySubmissionId` 컬럼을 유지한다.
   기존 항목 목록의 기본 범위는 그대로이고 `scope=all` 요청만 레거시 항목을
   포함한다. 명시적 항목 ID의 제출·심사·이력·파일 권한은 같은 팀 소속과
   같은 마일스톤으로 검증한다.
2. **프론트 전환:** 위 백엔드가 배포된 뒤 기존 체크리스트 구성에서
   `MilestoneDocumentSection`과 항목 API를 사용한다. 이전 프론트와
   준비 백엔드의 조합도 유지한다. 화면 차이는 전후 캡처와 함께 별도로
   검토하며 이 작업에서 머지하지 않는다.
3. **코드 참조 중단:** 전환된 프론트 배포 뒤 마일스톤 전용 API와
   레거시 판별 분기, 이전 심사 테이블 및 공개 ID 컬럼의 코드 참조를 없앤다.
   Todo 5의 purge 변경을 이 단계에서 통합한다. 물리 컬럼과 테이블은 유지한다.
4. **물리 삭제:** 코드 참조 중단 릴리스가 배포된 다음 별도 stacked draft의
   마이그레이션으로 사용하지 않는 컬럼과 심사 테이블을 삭제한다.
   마이그레이션이 앱 교체보다 먼저 실행되므로 앞 단계와 합쳐 배포하지 않는다.

## ID와 이력

공개 제출 ID의 PK 이동과 심사 이력 읽기·쓰기 전환은 백엔드 준비 릴리스에
속한다. 기존 backend는 공개 ID를 PK 또는 옛 ID 컬럼으로 조회하므로
같은 공개 ID를 계속 찾는다. FK는 `ON UPDATE CASCADE`로 이동한다.
이관 전에 충돌이 있으면 트랜잭션을 중단한다.

심사 이벤트와 원본 심사는 제출 ID·판정·처리자·시각·코멘트가 정확히
일치해야 한다. 기존 심사의 공개 ID와 코멘트를 그 이벤트에 보존한다.
마이그레이션 뒤 앱 교체 전의 이전 backend가 두 행을 쓰는 순서가 달라도
준비 트리거가 같은 ID를 유지한다. 새 backend는 한 이벤트만 쓴다.
이력 시각이나 누락된 revision을 추정하지 않는다.

준비 릴리스에서는 컬럼·테이블을 삭제하지 않는다. 후속 삭제 전까지 남는
원본 심사 테이블에는 새 backend가 기록하지 않으므로, 후속 삭제 단계의
대조는 준비 때 이관한 원본과 이후 생성한 이벤트를 구분해야 한다.
운영 데이터 복원 리허설과 실제 배포는 별개이며 이 작업은 운영 DB를 변경하지 않는다.

준비 배포 뒤 생긴 심사는 새 이력에만 있으므로, 롤백은 해당 쓰기까지 보존하는
대조·복구 절차가 필요하다. 이전 이미지만 다시 띄우면 새 심사를 옛 심사
테이블에서 읽을 수 없다. 이번 리허설은 준비 직전 백업의 복원까지 검증했으며,
운영에서 발생한 후속 쓰기의 다운그레이드 복구를 검증한 것은 아니다.

| --- | ---: |
| 공개 ID를 PK로 옮길 제출 | 20 |
| 공개 ID 충돌 | 0 |
| 레거시 항목 | 6 |
| 유형은 있지만 레거시 항목이 없는 마일스톤 | 2 |
| 유형이 없는 레거시 항목 | 0 |
| 원본 심사 / 대응 심사 이벤트 | 16 / 16 |

이 수치는 읽기 전용 집계다. 이후 릴리스 시점의 데이터 건수나 삭제 승인을
대신하지 않는다. 개인별 행, 덤프, 인증 정보는 증거에 포함하지 않는다.

## 입력과 심사 계약

항목의 입력 규칙은 별도 RequirementSubmissionType의 FILE, TEXT,
FILE_OR_TEXT로 표현한다. 기존 파일·텍스트 제출의 엄격한 규칙은 보존하고,
일반 서류는 텍스트만, 파일만, 둘 다를 허용한다. 선택 제출 코멘트와 관측한
expectedRevision을 항목 제출 API에서도 받는다.

모든 제출 심사의 사유는 선택이며 기존 코멘트는 보존한다. 재제출 기한 기능은
폐지한다. 준비 백엔드는 이전 프론트가 보내는 resubmissionDueAt을 무시하고
이력에 옮기지 않는다. 이전 응답 형식의 기한은 null로 보낸다. 프론트 전환에서
기한 입력·표시를 없앤다. 마일스톤 마감과 유예, 보완 요청당 마감 후 재제출
한 번의 규칙은 유지한다.

기존 필수 사유·필수 기한·기한 경과 차단 테스트는 선택 사유 저장, 이전 기한
요청 무시, 기한 없는 보완 후 재제출 검사로 교체한다. 자기 팀 심사 차단,
관측 revision 충돌, 판정 확정 후 재제출 금지 검사는 유지한다.
