## 위치와 검사 계약

계획의 `.omo/evidence/program-table-simplification/file-ledger.md`는 `.gitignore:35`의 `.omo/` 규칙에 걸린다. CI에서 읽을 추적 사본을 이 경로 `docs/evidence/program-table-simplification/file-ledger.md`에 둔다. `bun scripts/check-file-ledger.ts`의 기본 입력도 이 사본이다. 원장 경로를 첫 인수로 전달해 독립 검사가 가능하다.

Action은 최종 의도(`delete`/`merge`/`keep`), State는 실제 현재 상태(`present`/`deleted`)다. 병합·삭제 예정인 파일도 현재는 present이므로 존재해야 한다. 후속 Todo에서 파일을 제거한 뒤에만 deleted로 바꾼다. deleted 행의 원본이 남아 있거나, present 경로가 없거나, keep을 deleted로 표시하면 exit 1이다. ## Application ID 참조 인벤토리

기준 커밋의 제품 코드(백엔드·프론트엔드)와 Prisma schema를 조사했다. 과거 마이그레이션, 테스트 및 fixture는 제외했다. 아래는 `applicationId`/`applicationIds`(대문자 형태 포함), Application aggregate, APPLICATION target을 포함하는 모든 해당 줄이다. 파일당 줄 번호를 전부 기록하며 단순 타입 참조도 제외하지 않는다. 검색식은 `\bapplicationIds?\b|\bApplication\b|\bAPPLICATION\b`이며 같은 APPLICATION 토큰을 쓰는 User 도메인도 구별 없이 포함한다. 테스트·fixture·support 파일은 제외한다. 이전 목록의 누락된 SQL 테이블명·식별자 참조도 새 기준에서 다시 전수 집계했다. 이 목록은 마이그레이션 승인이나 운영 행 수의 증명이 아니다.

## 기준선 재현

`apps/backend`에서 `COMPOSE_PROGRESS=plain BACKEND_INTEGRATION_TEST_PATTERN='prisma/program-read-baseline.integration.spec.ts' bash test/run-integration.sh`를 실행한다. 실행기는 임시 PostgreSQL·object-storage를 만들고 migrate deploy 후 `pnpm exec jest --runInBand --testPathPattern=prisma/program-read-baseline.integration.spec.ts`를 호출한다(워크스페이스 명령 `pnpm --filter backend exec jest --runInBand prisma/program-read-baseline.integration.spec.ts`와 같은 스펙). 실행기의 EXIT trap이 컨테이너·볼륨·네트워크를 제거한다.

스펙은 격리 DB 가드를 먼저 통과해야 하며 고정 fixture를 만들고 측정 전 각 테이블 건수를 확인한다. `PROGRAM_READ_BASELINE_UNSEEDED=1`을 함께 설정하면 fixture 생성을 생략하고 `PROGRAM_READ_BASELINE_UNSEEDED` 오류로 실패한다. 테스트 완료 시 fixture를 정리하며 append-only AuditLog는 격리 DB의 정리 트랜잭션 안에서 해당 트리거만 잠깐 비활성화하고 즉시 다시 켠다. 이 작업은 운영 DB에서 실행할 수 없다.

네 실제 저장소 경로마다 warmup 1회와 순차 sample 20회를 기록한다. SQL 이벤트는 구독한 query 장벽으로 배출하고 장벽 SQL 자체는 수에서 제외한다. 장벽 시간은 p50에서 제외한다. 성능 수치에는 결과 검증 비용이 포함되며 HTTP·권한·직렬화 전체 지연은 아니다. 트랜잭션 제어 SQL과 팀 상세의 evidence SQL은 포함한다. 임계값 assert는 없다. p50은 10번째와 11번째 정렬 sample의 평균이다. 생성 결과는 `.omo/evidence/program-table-simplification/program-read-baseline.json`, 커밋 기준선은 이 디렉터리의 `program-read-baseline.json`이다.

테스트 시드는 소규모 합성 데이터이며 운영 성능을 대표하지 않는다. 두 마일스톤 모두 DOCUMENT 항목만 가지므로 레거시 제출 결과는 0건이다. 후속 단계는 동일 fixture·호스트 조건으로 재측정하고 운영 크기의 별도 검증 없이 속도 개선을 주장하지 않는다.
