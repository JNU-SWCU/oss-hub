# Todo 11 이름 변경과 원장 확정 검증

Todo 11은 세 PR로 나갔다. 1단계 #1763은 Prisma 모델 이름과 구조 표의 파일 통합, 2단계 #1766은 DB 테이블 이름 변경, 마무리 PR(이 브랜치 `refactor/program-simplification-final-cleanup`)은 죽은 값 정리와 원장 확정이다.
같은 주기에 프로그램 내림 상태 제거 #1764·#1765·#1762가 함께 나갔다.
이 문서에는 운영 행 데이터, 덤프, 개인 정보를 적지 않는다. 운영 수치는 배포 후 읽기 전용 검증의 집계 줄만 옮긴다.

## 범위

Todo 11은 DB 테이블·열·enum 타입 이름(2단계), Prisma 모델 이름과 구조 표의 파일 통합·이름(1단계)까지 바꿨다.
API 경로, 응답 필드, 오류 코드, enum 값은 wire 계약이므로 의도적으로 그대로 둔다.
내부 TS class·type·파일 이름의 `MilestoneDocument*` 잔재(계획 후속 12행 집계 기준 백엔드 제품 파일 47개, 프론트 제품 파일 55개)는 계획 후속 12행으로 미룬다.
고아 enum 타입 삭제는 13행, `auditLogWriter` 이름 변경은 14행이다.

## 최종 테이블

프로그램 도메인 테이블은 13개다: `Program`, `ProgramHistory`, `Milestone`, `Requirement`, `Team`, `TeamMember`, `TeamInvitation`, `TeamHistory`, `Submission`, `SubmissionHistory`, `File`, `BoardPost`, `BoardComment`.
이 브랜치의 `apps/backend/prisma/schema.prisma`에서 13개 모두 `model`로 있고 `@@map`이 없다. 따라서 Prisma 모델 이름이 DB 테이블 이름이다.

## 마무리 PR이 바꾸는 것

기준은 `aff9150be`(#1766 머지, v0.24.62)다. schema.prisma, 마이그레이션, DB는 바꾸지 않는다. 동작 변경 없이 죽은 코드와 값만 지운다. 파일별 상세와 남긴 것의 이유는 [파일 원장](file-ledger.md)의 「Todo 11 마무리」 절에 있다.

- 완전 삭제 응답 `deletedCounts`에서 늘 0이던 건수 18개를 지우고 `files`만 남겼다. 백엔드 저장소, 응답 DTO 타입, 프론트 타입과 완료 문구를 함께 줄였다. 완료 문구는 전과 같다.
- 삭제 범위 건수 SQL에서 같은 `Team` count 두 개를 하나로 줄였다. 응답의 `applications` 키는 wire 계약이라 `teams` 값으로 유지한다.
- 삭제 범위 fingerprint에서 쓰는 코드가 없는 `aggregateType = 'PROGRAM'` outbox 분기를 지웠다.
- `lock-program-tree.repository.ts`에서 두 분기가 같은 SQL이던 삼항식을 한 SQL로 줄였다.
- 프론트의 옛 저장소 발급 상태 `RETRYABLE_FAILED`·`FAILED`와 그 라벨, 그 값만 검사하던 테스트 경우를 지웠다.
- `deploy/jenkins/program-migration`에서 docs/evidence 밖 참조가 없는 단계 파일 18개(`requirement-rename/` 8개, `team-history/` 9개, `submission-axis-preflight.sql`)를 지웠다.
- `submissionReviewDecision` 공용화는 하지 않았다. 이유는 원장에 있다.

## 원장

`bun scripts/check-file-ledger.ts` 결과는 `FILE_LEDGER_OK 319 paths`다.
F1과 같은 방법(`apps/backend/src/programs/**/*.ts`에서 `spec`·`fixture`·`fixtures`·`test-support`·`integration-support`로 끝나는 파일 제외)으로 다시 쟀다.

| 시점 | files | lines |
| --- | ---: | ---: |
| #1766 머지 직전 main | 153 | 32244 |
| `aff9150be` (#1766 머지) | 153 | 32246 |
| 이 브랜치 | 153 | 32199 |

원장에 적혀 있던 2단계 32296은 1단계 수치 32294에 2를 더한 값이라 #1765의 −50줄이 빠져 있었다. 원장의 2단계 표를 실측값으로 고쳤다.
원장에는 Todo 11 범위 확정(계획 후속 12·13·14행으로 미룬 것), Todo 7 계획 대조 보정(계획 l.214의 `collection-sync.integration.spec.ts`는 저장소 이력에 없고 대신 쓴 스펙), 이 PR이 지우거나 바꾼 파일 37행을 더했다.

## 로컬 검증

`CI=true`가 아닌 로컬 셸에서, 앱 환경 변수를 비운 채 저장소 정의 명령으로 돌렸다. GitHub CI 결과를 근거로 삼지 않았다.
무거운 작업은 호스트에서 한 번에 하나만 돌렸다.
1차 전체 실행은 코드 수정을 마친 작업 트리에서 했다. 거기서 단위 테스트 1건이 실패했고(아래), 그 스펙 두 개만 고친 뒤 영향을 받는 단계를 2차로 다시 돌렸다. 제품 코드는 두 실행 사이에 바뀌지 않았다.

| 명령 | 결과 |
| --- | --- |
| 2차 `pnpm -r test` | 백엔드 379 suites·6022 tests·snapshot 279 통과, 프론트 439 files·4710 tests 통과 |
| 2차 `pnpm lint` | exit 0, 오류 0, 경고 4건(모두 이 PR이 건드리지 않은 프론트 파일의 `<a>` 경고) |
| 2차 `pnpm -r typecheck` | exit 0 |

| 2차 `pnpm format:check` | exit 0 |
| 2차 `node --test .design-sync/contract.test.mjs` | tests 7, pass 7, fail 0 |

| 1차 `node --test deploy/jenkins/program-migration/*.test.mjs` | tests 46, pass 46, fail 0 |

1차 실행의 단위 테스트 실패는 `program-editor-authority.repository.spec.ts`였다. 삭제 범위 SQL의 바인딩 값 수를 30개로 기대했는데, 중복 `Team` count와 PROGRAM outbox 분기를 지워 28개가 됐다. 의도한 변화이므로 기대값을 28로 고쳤고, 같은 SQL의 행 mock에서 지운 `applications` 열도 뺐다. `program-editor-update.repository.spec.ts`의 같은 mock도 정리했다.
1차 실행의 프론트 build 실패는 검증 스크립트가 `BACKEND_ORIGIN`을 비웠기 때문이다. CI와 같은 `BACKEND_ORIGIN=https://backend.example.test`로 2차에서 통과했다.
