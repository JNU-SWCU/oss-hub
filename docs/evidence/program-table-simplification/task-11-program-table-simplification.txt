# Todo 11 이름 변경과 원장 확정 검증

Todo 11은 세 PR로 나갔다. 1단계 #1763은 Prisma 모델 이름과 구조 표의 파일 통합, 2단계 #1766은 DB 테이블 이름 변경, 마무리 PR(이 브랜치 `refactor/program-simplification-final-cleanup`)은 죽은 값 정리와 원장 확정이다.
같은 주기에 프로그램 내림 상태 제거 #1764·#1765·#1762가 함께 나갔다.
이 문서에는 운영 행 데이터, 덤프, 개인 정보를 적지 않는다. 운영 수치는 배포 후 읽기 전용 검증의 집계 줄만 옮긴다.

## 범위

Todo 11은 DB 테이블·열·enum 타입 이름(2단계), Prisma 모델 이름과 구조 표의 파일 통합·이름(1단계)까지 바꿨다.
API 경로, 응답 필드, 오류 코드, enum 값은 wire 계약이므로 의도적으로 그대로 둔다.
내부 TS class·type·파일 이름의 `MilestoneDocument*` 잔재(계획 후속 12행 집계 기준 백엔드 제품 파일 47개, 프론트 제품 파일 55개)는 계획 후속 12행으로 미룬다.
고아 enum 타입 삭제는 13행, `auditLogWriter` 이름 변경은 14행이다.

## 마무리 PR이 바꾸는 것

기준은 `aff9150be`(#1766 머지, v0.24.62)다. schema.prisma, 마이그레이션, DB는 바꾸지 않는다. 죽은 코드와 값을 지우고, 화면에 보이는 변화는 감사 로그 action 라벨 하나(F3)뿐이다. 파일별 상세와 남긴 것의 이유는 [파일 원장](file-ledger.md)의 「Todo 11 마무리」 절에 있다.

- 완전 삭제 응답 `deletedCounts`에서 늘 0이던 건수 18개를 지우고 `files`만 남겼다. 백엔드 저장소, 응답 DTO 타입, 프론트 타입과 완료 문구를 함께 줄였다. 완료 문구는 전과 같다.
- 삭제 범위 건수 SQL에서 같은 `Team` count 두 개를 하나로 줄였다. 응답의 `applications` 키는 wire 계약이라 `teams` 값으로 유지한다.
- 삭제 범위 fingerprint에서 쓰는 코드가 없는 `aggregateType = 'PROGRAM'` outbox 분기를 지웠다.
- `lock-program-tree.repository.ts`에서 두 분기가 같은 SQL이던 삼항식을 한 SQL로 줄였다.
- 프론트의 옛 저장소 발급 상태 `RETRYABLE_FAILED`·`FAILED`와 그 라벨, 그 값만 검사하던 테스트 경우를 지웠다.
- `deploy/jenkins/program-migration`에서 docs/evidence 밖 참조가 없는 단계 파일 18개(`requirement-rename/` 8개, `team-history/` 9개, `submission-axis-preflight.sql`)를 지웠다.
- `submissionReviewDecision` 공용화는 하지 않았다. 이유는 원장에 있다.
- 프론트 문서 검토 표시 키 `PENDING`은 남겼다(F4 IS-3 재확인). 서버가 보내는 값이 아니라 프론트가 `SUBMITTED`나 상태 없음에서 계산하는 화면 키다. 이유는 원장에 있다.
- 감사 로그 action `APPLICATION_REPOSITORY_URL_CHANGED`에 라벨 `저장소 주소 변경`, 배지 색, 문장을 더했다(F3). 전에는 `기타 작업`과 원본 코드로 보였다. 목록 API의 `action` 필터가 이 값을 그대로 거른다.

## 성능 측정 (IS-6, 보고만)

보고만 하는 기록이다. 소유자 결정(`task-9-team-cutover.md`의 「소유자 최종 성능 결정」)에 따라 성능은 merge 조건이 아니며, 이 수치로 통과·실패를 판정하지 않는다. 로컬에서 한 번 돌린 결과라 호스트 잡음이 크다. 판단은 소유자가 한다. 운영 DB에서 재지 않았고 운영 데이터는 없다.

- 트리: R5 트리 `81c5c3610`(main `2c446c4db` + #1762 + #1766). push하지 않은 로컬 커밋을 임시 worktree에서 돌렸고, worktree는 지웠다.
- 명령: `apps/backend`에서 `test/run-integration.sh`, 패턴 `program-read-baseline\.integration\.spec\.ts$`. 실행 방법은 [파일 원장](file-ledger.md)의 「기준선 재현」과 같다. 실행기가 만든 임시 PostgreSQL에 migrate deploy로 106개 마이그레이션(`20261106100000`, `20261106200000` 포함)을 적용했다. 1 suite·1 test 통과, 실행기가 컨테이너·볼륨·네트워크를 지웠다.
- 같은 조건: 양쪽 모두 warmup 1회, sample 20회, 스펙의 고정 합성 seed다. 값을 덮어쓰지 않았다.
- 기준선: [`program-read-baseline.json`](program-read-baseline.json)(커밋 `a8262f757`, 2026-11-03). 이 파일은 고치지 않았다. R5 결과 JSON은 저장소에 두지 않았다.

## 로컬 검증

`CI=true`가 아닌 로컬 셸에서, 앱 환경 변수를 비운 채 저장소 정의 명령으로 돌렸다. GitHub CI 결과를 근거로 삼지 않았다.
무거운 작업은 호스트에서 한 번에 하나만 돌렸다.
1차는 첫 코드 수정을 마친 작업 트리, 2차는 아래 단위 테스트 실패로 백엔드 스펙 두 개만 고친 작업 트리, 3차는 감사 로그 라벨과 문서 검토 `PENDING` 정리를 더한 작업 트리의 전체 실행이다.
3차 뒤 `PENDING`은 남기기로 해 `milestone-document-review.ts`와 그 테스트를 `aff9150be`와 같게 되돌렸고, 안내서 한 문장과 증거 문서를 고쳤다. 이 최종 트리에서 프론트 단계와 형식·원장 검사를 4차로 다시 돌렸다.
백엔드 제품 코드와 `deploy/`는 1차 뒤로 바뀌지 않았다(백엔드는 2차에서 단위 스펙 두 개만 고쳤다). 그래서 통합 테스트·program-migration 테스트·shellcheck는 1차 결과를 적는다.

1차 실행의 단위 테스트 실패는 `program-editor-authority.repository.spec.ts`였다. 삭제 범위 SQL의 바인딩 값 수를 30개로 기대했는데, 중복 `Team` count와 PROGRAM outbox 분기를 지워 28개가 됐다. 의도한 변화이므로 기대값을 28로 고쳤고, 같은 SQL의 행 mock에서 지운 `applications` 열도 뺐다. `program-editor-update.repository.spec.ts`의 같은 mock도 정리했다.
1차 실행의 프론트 build 실패는 검증 스크립트가 `BACKEND_ORIGIN`을 비웠기 때문이다. CI와 같은 `BACKEND_ORIGIN=https://backend.example.test`로 2차·3차에서 통과했다.
3차와 최종 트리의 코드 차이는 되돌린 두 파일뿐이다. 3차의 그 파일은 같은 라벨·배지 상수를 `PENDING` 대신 `SUBMITTED` 키로 불렀고, 테스트 수는 같다. 최종 트리에서 e2e·build·백엔드 단계는 다시 돌리지 않았다.
프론트 tests가 2차(4710)보다 2개 많은 것은 감사 로그 라벨의 배지 표 한 줄과 문장 테스트 하나를 더했기 때문이다.
감사 로그 Before/After 캡처는 촬영용 임시 Playwright 스펙을 `aff9150be` worktree와 작업 트리에 복사해 찍고 지웠다. 그 스펙은 위 e2e 수에 들어 있지 않다.
안내서(`guide/`) 빌드는 로컬에서 돌리지 않았다. PR의 `guide-check` CI가 맡는다.
4차 뒤에는 이 증거 문서의 이 절만 고쳤다.
