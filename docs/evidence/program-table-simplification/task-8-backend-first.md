# Todo 8 A: 지명 지원 API 선행 배포

## 소유자 결정

최소 인원은 정확히 그 수가 아니라 **그 이상**이다. 지원 시 본인과 지명 학생 수가 최소 이상·최대 이하인지 검사한다. 지정만으로 가입시키지 않고, 최종 제출 트랜잭션이 Team·팀장 TeamMember·지원서·대기 초대를 함께 만든다. 승인 시에는 실제 TeamMember 수가 최소 이상이어야 한다. 최소 1명 프로그램만 혼자 지원할 수 있다.

이 문서는 기존 #1724의 “지원 인원을 검사하지 않는다”는 전제를 대체한다. 지원 시 검사와 승인 시 검사를 모두 유지한다.

## API와 호환

- 지원 요청에 선택적인 inviteeUserIds 배열을 추가했다. 기존 프론트는 이 필드를 생략해도 기존 준비팀 이름·수락 구성원을 사용해 지원할 수 있다. 기존 준비팀도 최소 인원 미달이면 거부하고 준비 상태를 보존한다.
- 가입한 활성 학생을 프로그램별로 검색한다. 팀이나 준비팀을 먼저 만들 필요가 없다. 검색과 지원 모두 학생 자격을 검사한다.
- 중복 지명·자기 지명·인원 초과·부적격 계정·동일 프로그램의 기존 소속을 거부한다. Program 잠금 아래에서 기준을 읽고 대상 User를 정렬해 잠근 뒤 현재 자격을 검증한다. 기존 준비팀과 새 지명 인원의 사용자 잠금을 한 번에 잡아 잠금 순서를 유지한다.
- 지명된 사람은 수락하기 전까지 TeamMember가 아니다. 거절 후 다른 학생에게 초대할 수 있고, 그 사이 다른 팀에 가입했다면 수락을 거부한다.
- 프로그램 상세에 teamMinSize/teamMaxSize, 교직원 팀 관리 응답에 teamMinSize를 추가했다. team.memberCount가 실제 수락 인원이며 기존 응답 필드는 유지한다.

## 배포 순서

1. A를 먼저 배포한다. 기존 프론트는 준비팀 흐름을 계속 사용한다.
2. Jenkins가 A 포함 백엔드를 실제 서빙하고 정상 상태임을 확인한 뒤에만 B draft를 해제하고 프론트를 배포한다. Vercel은 release publish로 별도 실행되며 Jenkins를 기다리지 않는다.
3. TeamHistory 이관·옛 쓰기 중단, 그 다음 물리 DROP은 별도 후속 릴리스다. 이번 작업에서는 시작하지 않았다.

## 행동과 경합 증거

새 계약의 최초 red는 13개 중 11개 실패했다. 기존 #1724가 지명 인원을 무시하고 최소 2명인 프로그램의 혼자 지원을 허용하는 것을 재현했다. 이후 실제 DB 통합 3 suites / 51 tests가 통과했다. 최소 1명 혼자 지원, 최소보다 많은 인원 지정, 각 지명 거부 조건, 수락 전 승인 거부, 거절 후 대체 인원 수락·승인, 다른 팀 합류 후 수락 거부, 마지막 감사 기록 실패 시 팀·지원·초대 전체 롤백을 확인한다. 최소보다 많은 실제 수락 인원도 승인할 수 있는 단언을 포함한다.

기존 준비팀 호환과 승인·탈퇴 잠금 테스트를 유지했다. 탈퇴 트랜잭션이 Team 잠금을 보유할 때 승인 연결의 PostgreSQL Lock 대기를 관찰하고, 탈퇴 커밋 후 줄어든 인원으로 APP_019를 반환하는 테스트다. 이전에 같은 Team 잠금만 제거한 mutation이 해당 테스트에서 실패하는 것을 확인했다. sleep과 재시도 통과 옵션은 없다.

수락 중 승인도 같은 경합 테스트에 추가했다. 최초 실행에서 승인 인원은 새 값으로 통과하지만 저장소 발급 outbox에서 방금 수락한 학생이 빠지는 실패를 재현했다. Team 잠금 이후 구성원을 다시 읽어 알림·발급 대상에 사용하고, 최초 상태는 조건부 상태 전이용으로 유지했다. 두 경합을 포함한 신청 통합 28개와 판정 단위·HTTP 175개가 통과했다. 새 초대 fixture의 정리 범위 누락도 수정했으며 후속 FK 실패를 제품 실패로 집계하지 않았다.

라우트 계약 기준선에는 새 보호 검색 경로만 추가했다. JSON 스냅샷에는 실제 인원 필드만 추가했으며 기존 필드와 기대를 삭제하지 않았다. 계정·시간·외부 서비스는 합성 fixture이며 데이터베이스는 빈 DB에서 기존 마이그레이션을 적용한 격리 PostgreSQL이다.

최종 영수증: 지정 경계 15개, 신청·판정·수락/탈퇴 경합 28개, 기존 준비팀 9개를 확인했다. backend 전체 390 suites / 6,337 tests 및 309 snapshots가 통과했다. backend typecheck·lint, 구조·포맷·파일 원장도 EXIT=0이다. UI 소비 검증은 학생·교직원 두 폭 4개 시나리오와 최종 학생 캡처 2개가 통과했고, 가이드용 DPR 2 캡처와 guide build도 EXIT=0이다.

## 화면 증거와 검토 범위

백엔드 PR이라는 이유로 화면 증거를 면제하지 않는다. A API를 소비하는 후속 B 후보의 지명 전·후, 제출 후 대기 초대, 수락 1/2명과 승인 거부를 실제 Chrome 두 폭에서 캡처해 PR에 붙인다. 화면 소스는 B 후보이고 API는 page.route 합성 응답이라는 한계를 명시하며, 저장·인가·원자성은 위 실제 DB 검증으로 분리해 증명한다. A 자체는 프론트 제품 코드를 바꾸지 않는다.

기존 큰 서비스·저장소는 이번 단계의 트랜잭션과 기존 준비팀 호환 경계를 유지하기 위해 분리하지 않았다(SIZE_OK). 분리하면 같은 transaction을 전달하는 facade만 늘고 Todo 9의 승인된 팀 지원 통합과 중복된다. 신규 테스트는 구성 fixture와 행위 검증을 분리해 각 파일의 순수 코드 250줄 이내로 유지한다.

## 데이터와 정리

운영 데이터 이관·삭제는 0건이다. schema와 migration 변경이 없어 서버 내부 실데이터 이관 리허설은 해당하지 않는다. 이전 읽기 전용 집계의 종료 초대 이관 후보는 수락 20 + 거절 5 = 25건이며, 실제 이관 때 다시 집계해야 한다. 테스트 실행기는 자신이 만든 DB 컨테이너와 볼륨을 정리한다. heavy lock은 획득한 실행만 해제한다.
