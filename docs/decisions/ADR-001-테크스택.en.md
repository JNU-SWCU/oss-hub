# ADR-001: Technology Stack

[한국어](ADR-001-테크스택.md) | **English**

English translation of the [Korean source](ADR-001-테크스택.md).
The Korean document remains authoritative.

## Status

Accepted

## Date

2026-07-11

## Context

The initial repository develops the frontend and backend together and needs to minimize differences in database behavior between development and production.
Developers run applications with hot reload through `pnpm` and run only the database in a Docker container.
The runtime needs to be pinned to the currently active Node.js LTS, with clear responsibilities for the workspace, web application, API, ORM, and database.

## Decision

Use only `pnpm workspaces` for package management and declare Node.js 24 LTS in `engines`.
The repository consists of Next.js in `apps/frontend` and NestJS in `apps/backend`.
Use Prisma ORM for backend data access and PostgreSQL as the relational database in all environments, including development and production.

`pnpm` provides strict dependency management and efficient disk usage, and workspaces alone meet the current monorepo requirements.
Prisma provides a type-safe client, schema-based migrations, Prisma Studio, and strong ecosystem momentum.
Using PostgreSQL in every environment allows development DB initialization through Docker, eliminating the need for an in-memory substitute and differences in SQL dialects.
Node.js 24 is the active LTS, providing a security and maintenance support window.

## Alternatives considered

### npm/yarn workspaces

- Pros: Familiar standard tools with a low adoption barrier.
- Cons: They do not offer `pnpm`'s consistent operational model for dependency isolation and disk efficiency.
- **Rejected:** For the current requirements, using only `pnpm workspaces` provides simpler, more reproducible dependency management.

### TypeORM

- Pros: Widely used in the NestJS ecosystem and supports decorator-based modeling.
- Cons: Its type-safe query experience and consistency across schemas, migrations, and management tools are weaker than Prisma's.
- **Rejected:** Prisma's type safety, migrate, Studio, and ecosystem momentum better suit the initial team's productivity.

### In-memory development database

- Pros: Enables a quick start without a separate DB container.
- Cons: Differences in SQL features and dialects from PostgreSQL can hide defects before production.
- **Rejected:** Docker DB initialization offers development convenience while preserving PostgreSQL parity across all environments.

## Consequences

### Enables

- Manage independently deployable frontend and backend units in one workspace.
- Reduce differences in database behavior between development and production and track schema changes through migrations.
- Establish a basis for type checking between DTOs and ORM models.

### Costs / trade-offs

- Developers must install Node.js 24 and `pnpm` and run a PostgreSQL container.
- Follow the update procedure for the Prisma schema and generated client.

### New constraints

- Every package must comply with the Node.js 24 LTS engines declaration.
- Run applications on the host through `pnpm` and only the development DB in a Docker container.
- Use PostgreSQL in both production and development.
